## Three, Why Loki Has Multiple Deployment Modes

Loki is a modular architecture.

It contains multiple logical components:

    Distributor
    Ingester
    Querier
    Query Frontend
    Query Scheduler
    Compactor
    Ruler
    Index Gateway
    Gateway

These components can:

    Run in the same process
    Run grouped by read / write / backend
    Run as completely independent components

Thus forming different deployment modes:

    Monolithic
    Simple Scalable
    Microservices

Deployment modes essentially make trade-offs between the following goals:

    Simplicity
    High availability
    Scalability
    Cost
    Operation complexity
    Query performance
    Write throughput
    Storage reliability
    Fault localization difficulty

It cannot be simply understood as:

    More Pods mean more advanced
    More components mean more production-ready
    Monolithic mode is definitely not usable
    Microservices mode is always the best

The correct understanding is:

    The more logs, the higher the query concurrency, the more complex the multi-tenancy, the more the need to split.
    Learning and small-scale environments should prioritize simplicity.
    Production should combine log volume, SLA, team capabilities, and maintenance costs.

## Four, Overview of Loki's Three Deployment Modes

### 4.1 Monolithic / Single Instance Mode

Also commonly referred to as:

    Single Binary

Core characteristics:

    Loki's multiple components run in a single process.

Common Kubernetes resource forms:

    One StatefulSet
    One or more Loki Pods
    One Service
    Optional Gateway
    Optional PVC
    Optional object storage

Logically, it still includes:

    Distributor
    Ingester
    Querier
    Compactor
    Ruler

But at the Kubernetes resource level, these components may not be visible as separate independent Pods.

### 4.2 Simple Scalable / Simple Scalable Mode

Core Features:

    Loki splits components into three roles: read / write / backend.

Common Roles:

    read:
        Query-related components.

    write:
        Write-related components.

    backend:
        Background task components.

Common Kubernetes Resource Forms:

    loki-read
    loki-write
    loki-backend
    loki-gateway

Notes:

    Simple Scalable Deployment is currently marked as deprecated by the official team.
    The deprecation timeline still requires attention to the official documentation.
    Due to its widespread existence in historical environments, it's still necessary to understand for learning purposes.
    When selecting for new production environments, careful evaluation of versioning is required.

### 4.3 Microservices / Distributed / Microservices Mode

Core Features:

    Loki components run as independent services.

May Include:

    distributor
    ingester
    querier
    query-frontend
    query-scheduler
    compactor
    ruler
    index-gateway
    gateway

Common Kubernetes Resource Forms:

    Multiple Deployments
    Multiple StatefulSets
    Multiple Services
    Multiple HPA / PDB / ServiceMonitor
    Object storage
    Cache components

Suitable For:

    Large-scale production
    Multi-tenancy
    High write volume
    High query concurrency
    Unified maintenance by platform teams

## Five. Deployment Mode Comparison Table

| Comparison Item | Monolithic | Simple Scalable | Microservices |
|---|---|---|---|
| Complexity | Low | Medium | High |
| Learning Friendliness | High | Medium | Low |
| Component Splitting | Not obvious | read/write/backend | Fully split |
| Read/Write Independent Scaling | Weak | Better | Strong |
| High Availability | Limited, can be enhanced | Better | Strong |
| Storage Requirements | Can be local/PVC/object storage | Usually requires object storage | Usually requires object storage |
| Query Performance Tuning | Simple | Medium | Strongest |
| Write Performance Tuning | Simple | Medium | Strongest |
| Troubleshooting Difficulty | Low | Medium | High |
| Suitable for Learning | Very suitable | Can be used as an advanced option | Not suitable for beginners |
| Suitable for Small Scale | Suitable | Suitable | Complexity is relatively high |
| Suitable for Medium Scale | Can be cautiously used | Historically suitable, but needs to monitor deprecation | Suitable |
| Suitable for Large Scale | Not suitable | Needs cautious consideration | Suitable |
| Version Risk | Low | Current deprecation risk | Long-term production direction |

## Six. Key Metrics for Deployment Mode Selection

### 6.1 Log Write Volume

Need to Pay Attention to:

    How many logs are written daily
    How many logs are written per second
    Average size of single log
    Whether there are log peaks
    Whether there areMass DEBUG logs
    Whether there are abnormal screen floods

General Understanding:

    Small Log Volume:
        A single instance mode is sufficient for learning and verification.

    Medium Log Volume:
        Requires object storage, reasonable resources, and query limits.

    Large Log Volume:
        Requires read/write splitting, caching, rate limiting, object storage, and component-level scaling.

### 6.2 Query Concurrency

Need to Pay Attention to:

    How many people query logs simultaneously
    Whether multiple teams use it
    Whether there are large-scale queries
    Whether there are continuous queries from Dashboards
    Whether there are frequent executions of log alert rules
    Whether query time ranges often exceed several hours or days

In environments with high query pressure, typically focus on:

    Query Frontend
    Querier
    Cache
    Object Storage performance
    Query limits
    Dashboard query range

### 6.3 Retention Period

Need to Pay Attention to:

    Log retention for 7 days
    Log retention for 15 days
    Log retention for 30 days
    Log retention for 90 days
    Whether different namespaces have different retention periods

The longer the retention period:

    Larger storage
    Compactor becomes more important
    Object storage becomes more important
    Query limits become more important

### 6.4 Multi-tenancy

Need to Pay Attention to:

    Whether multiple teams share it
    Whether team isolation is needed
    Whether tenant-based rate limiting is needed
    Whether different retention policies are needed
    Whether permission control is needed
    Whether auditing is needed

Multi-tenancy environments are generally more suitable for a more complete production architecture.

### 6.5 Operations Team Capabilities

Need to realistically assess:

    Whether someone maintains Loki
    Whether someone understands Loki's own metrics
    Whether someone can troubleshoot object storage
    Whether someone can handle slow queries
    Whether someone can govern label cardinality
    Whether someone can tune compactor / ruler / cache

If the team is just starting to learn Loki, it's not recommended to directly use complex modes.

## 8. Simple Scalable Mode Detailed Explanation

### 8.1 Architecture Diagram

    Alloy / Fluent Bit
      ↓
    Loki Gateway
      ↓
    write
      ├── Distributor
      └── Ingester
      ↓
    Object Storage

    Grafana
      ↓
    Loki Gateway
      ↓
    read
      ├── Query Frontend
      └── Querier
      ↓
    Object Storage / Ingester

    backend
      ├── Compactor
      ├── Ruler
      └── Index Gateway

### 8.2 Three Roles

#### write

Responsible for log ingestion path.

Includes capabilities:

    Distributor
    Ingester

Main processing:

    Receive logs
    Validate writes
    Rate limiting
    Chunk splitting
    Write to WAL
    Flush to storage

#### read

Responsible for log query path.

Includes capabilities:

    Querier
    Query Frontend

Main processing:

    Execute LogQL
    Query splitting
    Query caching
    Query object storage
    Query latest data

#### backend

Responsible for background tasks.

Includes capabilities:

    Compactor
    Ruler
    Index Gateway

Main processing:

    Index compression
    Retention period cleanup
    Log alert rules
    Background maintenance tasks

### 8.3 Kubernetes Resource Types

May see:

    loki-read-xxx
    loki-write-xxx
    loki-backend-xxx
    loki-gateway-xxx

Commands:

    kubectl get pods -n logging -o wide

    kubectl get deploy,statefulset -n logging

    kubectl get svc -n logging

### 8.4 Advantages

Advantages:

    Separation of read/write.
    Easier to scale than monolithic mode.
    Fewer components than microservices.
    Easier to understand than microservices mode.
    Suitable for intermediate stage learning production concepts.
    Can separately observe read/write/backend pressure.

### 8.5 Disadvantages

Disadvantages:

    More complex than monolithic.
    Depends on object storage.
    Still not the finest-grained component split.
    Officially marked as deprecated.
    Caution is needed for version route confirmation before new production environments.
    May need migration to other modes in the future.

### 8.6 How to View Simple Scalable Currently

For learning:

    Still worth understanding.
    Because it helps understand Loki read/write splitting.
    Many historical environments still use similar patterns.
    The read/write/backend logic helps understand production architecture.

For production:

    New environments shouldn't blindly choose.
    Need to pay attention to official version changes and Loki 4.0 changes.
    Need to evaluate whether to directly adopt Monolithic HA or Microservices/Distributed.
    Existing environments need migration planning.

This series arrangement:

    Not use Simple Scalable as the main deployment in the early stage.
    Chapter 13 will be observed as a performance and HA entry mode.
    Focus on learning the split idea of read/write/backend, not treat it as a long-term recommendation.

## Ten, Deployment Mode and Storage Relationship

### 10.1 Local File System

Suitable:

    Learning  
    Temporary verification  
    Minimal experiment in monolithic mode

Advantages:

    Simple  
    Few configurations  
    Fast deployment

Disadvantages:

    Risk of Pod recreation  
    Risk of node failure  
    Limited capacity  
    Not suitable for multiple replicas  
    Not suitable for long-term production storage

### 10.2 PVC

Suitable:

    Enhanced learning environment  
    Small-scale environment  
    Persistent storage in monolithic mode  
    Initial verification of retention period

Advantages:

    More reliable than emptyDir  
    Data is preserved after Pod recreation  
    Native Kubernetes management

Disadvantages:

    Strongly related to storage class  
    Limited high availability  
    Limited scalability  
    Caution is needed for multi-replica sharing  
    Less suitable for long-term log storage than object storage

### 10.3 Object Storage

Suitable:

    Production  
    Medium to large-scale logs  
    Multiple replicas  
    High availability  
    Long-term storage  
    Scalable capacity

Common object storage:

    MinIO  
    AWS S3  
    Alibaba Cloud OSS  
    Tencent Cloud COS  
    Huawei Cloud OBS  
    GCS  
    Azure Blob

This series uses:

    MinIO

Reasons:

    Easy to deploy locally.  
    S3 compatibility.  
    Suitable for experiments.  
    Convenient for observing data in bucket.

### 10.4 Recommended Relationship

First step for learning:

    Monolithic + Local / PVC

Second step for learning:

    Monolithic + MinIO

Production for small-scale:

    Combine with official version roadmap, evaluate Monolithic HA + object storage or Microservices

Production for large-scale:

    Microservices / Distributed + object storage + caching + complete monitoring

## Eleven, Deployment Mode and Gateway Relationship

### 11.1 What is Gateway

Gateway is typically a unified entry point for Loki.

In Helm deployment, it is commonly implemented as Nginx.

It is responsible for:

    Receiving write requests  
    Receiving query requests  
    Forwarding to corresponding Loki backend based on path  
    Exposing a unified Service  
    Simplifying client configuration

### 11.2 Why Need Gateway

Without Gateway, collectors may need to know:

    Write component address  
    Query component address  
    Ruler address  
    Multiple Service addresses

With Gateway, collectors only need:

    http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push

Grafana only needs to configure:

    http://loki-gateway.logging.svc.cluster.local

### 11.3 Gateway Role in Different Deployment Modes

Monolithic:

    Gateway is optional.  
    Small-scale can directly access Loki Service.  
    Using Gateway can approach production entry earlier.

Simple Scalable:

    Gateway is very important.  
    Responsible for forwarding writes and queries to different roles.

Microservices:

    Gateway is a key component for unified entry.  
    Used to hide backend component complexity.

## Twelve, Deployment Mode and Alloy Relationship

Alloy is the collector, not part of Loki server deployment mode.

Regardless of Loki's deployment mode, Alloy is responsible for:

    Collecting Pod logs  
    Adding Kubernetes labels  
    Forwarding logs to Loki

The difference is only in the address Alloy writes to.

### 12.1 Monolithic

Alloy can write to:

    http://loki.logging.svc.cluster.local:3100/loki/api/v1/push

Or through Gateway:

    http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push

### 12.2 Simple Scalable

Usually write to Gateway:

    http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push

Gateway forwards to write component.

### 12.3 Microservices

Usually write to Gateway:

    http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push

Gateway forwards to distributor.

## Thirteen, Deployment Mode and Grafana Relationship

Grafana is the query entry point.

Regardless of Loki's backend mode, it is recommended to access a unified entry point when configuring Loki Data Source in Grafana.

### 13.1 Monolithic

Grafana can access:

    http://loki.logging.svc.cluster.local:3100

Or:

    http://loki-gateway.logging.svc.cluster.local

### 13.2 Simple Scalable

Grafana usually accesses:

    http://loki-gateway.logging.svc.cluster.local

Gateway forwards to read component.

### 13.3 Microservices

Grafana usually accesses:

    http://loki-gateway.logging.svc.cluster.local

Gateway forwards to query-frontend / querier.

## Twenty-Three, Common Issues

### 23.1 helm template reports field not found

Possible reasons:

  Chart version change.
  values field name change.
  deploymentMode value change.
  SingleBinary / Monolithic field change.
  SimpleScalable / Distributed name change.

Handling:

  helm show values grafana/loki > values-loki-default.yaml

  grep -n "deploymentMode" values-loki-default.yaml

  grep -n "monolithic" values-loki-default.yaml

  grep -n "singleBinary" values-loki-default.yaml

Use current version values as reference, do not copy old article configurations.

### 23.2 Why do I see singleBinary instead of monolithic

Reason:

  Different Helm Chart versions may have different fields.
  Old versions commonly use SingleBinary.
  New versions may use Monolithic.
  Chart migration and version changes cause field changes.

Handling principle:

  Conceptually understand as monolithic mode.
  Operationally use current chart values fields as reference.

### 23.3 Can Simple Scalable still be learned

Yes.

But clarify:

  Learning it is to understand read/write/backend.
  It is not recommended as default for new production environments.
  Production selection must continuously follow official documentation and version roadmap.

### 23.4 Why isn't the learning environment directly using Microservices

Reason:

  Components are numerous.
  Configuration is complex.
  Troubleshooting is complex.
  It may interfere with understanding Loki's basic pipeline.
  Object storage, caching, and monitoring require more complete planning.
  Low ROI in early learning stages.

Learning order should be:

  First run a simple setup
  Then understand query and collection
  Then understand storage and alerts
  Finally understand high availability and scalability

### 23.5 Is monolithic mode unsuitable for production

Cannot say that absolutely.

Small scale, low log volume, internal environments can be evaluated for use.

But production must supplement:

  Persistent storage
  Object storage
  Resource limits
  High availability design
  Self monitoring
  Alerts
  Retention
  Backup and recovery
  Access control
  Query limits
  Label governance

  Object storage capacity
  Object storage performance
  Deletion permissions
  Lifecycle policies

### 24.3 Label governance is more important than component count

Poor label design can directly undermine Loki.

High-risk labels:

  request_id
  trace_id
  user_id
  order_id
  session_id
  full_url
  error_message
  stacktrace

Recommended labels:

  cluster
  environment
  namespace
  pod
  container
  node
  app
  team

### 24.4 Query limits must be implemented

In production, need to limit:

  Maximum query time range per query
  Maximum log lines per query
  Query concurrency
  Query timeout
  Per-tenant query resources
  Per-tenant write rate
  Per-tenant stream count

Otherwise, a large query range may affect the entire Loki.

## Twenty-Six, Summary

Loki is not only a single deployment method.

Common deployment patterns include:

    Monolithic:
        Single-node pattern, most suitable for learning, small-scale environments, and rapid validation.

    Simple Scalable:
        Split read/write/backend pattern, historically used for medium-scale expansion, but the official has marked it as deprecated and needs cautious consideration.

    Microservices / Distributed:
        Fully split components, suitable for large-scale production, multi-tenancy, high write throughput, and high query concurrency scenarios.

This series selects:

    Early stage:
        Monolithic

    Collection:
        Grafana Alloy

    Query:
        Grafana Explore

    Storage evolution:
        PVC / File system → MinIO object storage

    Alerting:
        Loki Ruler → AlertManager

Core principles:

    First ensure the end-to-end flow works.
    Then understand labels.
    Then learn querying.
    Then integrate alerts.
    Then implement production governance.
    Finally learn high availability and scalability.

Don't pursue complex architecture from the beginning.

True production capability isn't "deploying many Pods", but:

    Full log collection
    Reasonable label design
    Controllable querying
    Accurate alerts
    Reliable storage
    Cost control
    Fault diagnosis
    Sustainable operations
