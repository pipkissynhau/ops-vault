## I. What Was Achieved in This Phase

The core of the node-level application deployment section is not to learn all the details of a specific component, but to establish a new way of understanding workload models.

The main tasks completed in this phase include:

- Basics of DaemonSet
- Comparison of three types of workload models: Deployment, StatefulSet, and DaemonSet
- Detailed analysis of node-exporter deployment at the node level
- Understanding why DaemonSet is commonly used for log collectors

Through these topics, a clear understanding can be formed:

> **Some components are not designed to provide external business services or maintain a set of stateful members, but rather to offer certain local capabilities on each node.**

These types of components are known as node-level applications.

---

## II. Why node-exporter Is a Natural Starting Point for Node-Level Applications

node-exporter is the most natural starting point for understanding node-level applications because its purpose is very clear:

- Collecting native node metrics
- Exposing metrics APIs
- Providing data for Prometheus to retrieve
- Ensuring an instance exists on each node

Through node-exporter, it becomes easier to understand the core value of DaemonSet:

### 1. It focuses more on node coverage rather than the number of replicas
If a cluster has 6 nodes, the typical expectation is:

- Each of the 6 nodes should have one node-exporter instance

Rather than:

- Running only 2 or 3 instances across all nodes

### 2. It is closer to the host machine
It often involves:

- `/proc`
- `/sys`
- The host machine's root directory
- `hostNetwork`
- `hostPort`

### 3. It is not a business service but a node proxy
Its role is not to handle business requests but to output monitoring data on behalf of the nodes.

### Key Points for Ops Professionals
The example of node-exporter demonstrates that when deploying node-level applications, the first thing to understand is not the image itself, but:

> **Whether the component's responsibilities are inherently tied to each node.**

## III. What Really Changes When Migrating from node-exporter to Log Collectors

Log collectors represent the second most common category of node-level applications.

Common examples include:

- Fluent Bit
- Filebeat

Like node-exporter, they also often use DaemonSet, but their collection targets are different.

### What node-exporter Collects
It mainly collects:

- CPU usage
- Memory consumption
- File system information
- Network interface status
- System load and other node metrics

### What Log Collectors Collect
They primarily collect:

- `/var/log/containers`
- `/var/log/pods`
- Host machine system logs
- Local log files generated by specific applications

### Their Commonalities
- Both are well-suited for deployment using DaemonSet
- Both usually require node coverage
- Both are closely integrated with the host machine's perspective
- Both act as platform proxy components

### Their Differences
- node-exporter outputs metrics
- Log collectors output logs
- node-exporter focuses more on reading system status
- Log collectors focus more on reading log files and forwarding them to logging platforms

### Key Points for Ops Professionals
When migrating from node-exporter to log collectors, there is no need to relearn the entire DaemonSet model. It is sufficient to understand that:

> **Although both are node proxies, they differ in the type of data they read and output.**

## X. Final Conclusion of This Phase

In the deployment of node-level applications, what is actually established is not specialized knowledge about certain monitoring or logging components, but a set of analysis methods tailored for “node-agent-type components.”

The core of this method includes:

- First, determine whether node coverage is required.
- Next, determine whether host machine visibility is needed.
- Then, consider whether it is necessary to be closer to the host machine’s network or namespace.
- Finally, assess the relationship between its output objects and the platform.

Starting with node-exporter and extending this approach to logging collectors, security agents, CNI, and CSI node components, a comprehensive framework has been established.

Up to this point, **04-Node-Level Application Deployment** can be considered completed for now.

## XI. Quick Reference Terms

- Node-level application: Platform-agent-type components that operate on a per-node basis.
- DaemonSet: Node coverage controller.
- node-exporter: Agent for collecting node metrics.
- Fluent Bit / Filebeat: Agents for collecting node logs.
- Security Agent: Agent for node security checks and audits.
- CNI node component: Component that enhances node networking capabilities.
- CSI node component: Component that manages node storage mounting.
- hostPath: Mounting of host machine directories on nodes.
- Node coverage: Each node has an instance of the component.
- Host machine visibility: The component is able to read or perceive the resources of the node itself.

---

## XII. Further Understanding of Operations and Maintenance

In Kubernetes, the difficulties in deployment often lie not in the YAML code itself, but in the operational models behind the components.

- MySQL represents stateful business systems.
- node-exporter represents node monitoring agents.
- Fluent Bit / Filebeat represent node logging agents.
- Security Agent, CNI, and CSI node components represent platform-side node capability components.

Although these components all run within Kubernetes, they address different issues:

- How to scale out stateful services.
- How to maintain data and identity in stateful services.
- How to distribute node agents across nodes.
- How to make platform components work more closely with the host machine.

By understanding these models at a hierarchical level, subsequent studies on Helm, application deployment, updates, and rollbacks will be more straightforward and effective.
