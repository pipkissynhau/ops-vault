## I. Why Log Collectors Are Ideal for Node-Level Applications

In node-level applications, log collectors represent a very common type of component.

The previous example of node-exporter illustrates:

- Collection of node metrics
- Monitoring of host resources
- One monitoring agent per node

On the other hand, log collectors address another essential node-level capability:

- Collection of container logs
- Collection of host machine logs
- Log forwarding
- Centralized log aggregation

Although both log collectors and node-exporter are commonly deployed using DaemonSets, they solve different problems.

### What Does node-exporter Focus On?
It focuses more on:
- CPU usage
- Memory consumption
- File systems
- Network interfaces
- Node resource metrics

### What Do Log Collectors Focus On?
Log collectors focus on:
- Pod log files
- Host machine log directories
- Locations where container runtime generates logs
- Forwarding logs to downstream platforms

Therefore, log collectors make an ideal second example of components deployed using DaemonSets.

## II. Why Are Log Collectors Usually Deployed as DaemonSets Rather Than Deployments?

The key reason lies not in what official examples recommend but in the way log collection itself works.

### 1. Logs Are Naturally Distributed Across Nodes
In Kubernetes, container logs are usually not stored in one central location but are distributed across various nodes.

For example:
- Logs generated by business Pods on Node A are typically stored on Node A.
- Logs generated by business Pods on Node B are typically stored on Node B.

This means that if a log collector does not run directly on the nodes, it will be difficult to efficiently collect logs from all nodes.

### 2. The Goal Is Not to “Run Multiple Collection Instances” but to “Cover All Nodes”
If a log collector only has two Deployment instances and the cluster consists of eight nodes, the following issues will arise:

- Some nodes will have log collectors.
- Some nodes will not have log collectors.
- Node coverage will be incomplete.

### 3. New Logs Should Be Automatically Collected When New Nodes Are Added
Whenever a new node is added to the cluster, as long as there are business Pods that may be scheduled to run on it, that node should also have a corresponding log collector.

### Key Points for Operations and Maintenance Professionals
The goal of a log collector is not:

> To run a certain number of instances in total

but rather:

> To ensure that all nodes have the capability to collect logs.

This is precisely the workload model that DaemonSets are best suited for.

## III. What Types of Logs Are Usually Collected by Log Collectors in Kubernetes?

At this stage, there is no need to go into detail about all the features of Fluent Bit or Filebeat. It is sufficient to get a general understanding of what types of logs are collected.

### Common Types of Logs Collected Include

#### 1. Standard Container Output Logs
This is the most common type.

Many business containers print logs to the standard output, and Kubernetes and the container runtime store these logs in log files on the nodes.

#### 2. Host Machine System Logs
For example:
- `/var/log/messages`
- `/var/log/syslog`
- `/var/log/dmesg`
- Audit logs
- Security-related logs

#### 3. Logs in Specific Application Log Directories
If business containers or host machine processes write logs to specific directories, log collectors may also directly read from these paths.

### A Key Concept
The focus of a log collector is not simply “reading the standard output inside the container” but rather:

> **Reading log files from the node perspective and then forwarding them to the log platform.**

## IV. Why Are Fluent Bit and Filebeat Commonly Deployed Using DaemonSets?

Fluent Bit and Filebeat are both very popular log collectors. Although their implementations differ, their node-level deployment approaches in Kubernetes are quite similar.

### Commonality 1: Both Require Node Coverage
Every node must have the capability to collect logs.

### Commonality 2: Both### Summary of this Phase

The reason why log collectors like Fluent Bit and Filebeat commonly use DaemonSets is quite straightforward:

- Logs are naturally distributed across various nodes.
- Collectors need to be close to these nodes.
- When new nodes are added, instances should automatically be created.
- When nodes are removed, corresponding instances should disappear.

Components like these, similar to node-exporter, are typical node-level applications. However, their purposes differ:

- node-exporter focuses on node metrics.
- Log collectors focus on collecting logs from nodes.

Understanding this distinction helps when considering other node-level components: ask yourself whether they aim to utilize the native capabilities of nodes or provide external services.

## Quick Reference Terms

- **DaemonSet**: A node-level controller designed for widespread node coverage.
- **Fluent Bit / Filebeat**: Common log collectors.
- **hostPath**: Mounting host directory paths for log access.
- `/var/log/containers`: A common container log path.
- **Log forwarding**: The process of sending logs to downstream platforms.
- **Kubernetes metadata**: Context information such as Namespace, Pod, Container, and Node.
- **Log platform**: Systems responsible for storing, retrieving, and analyzing logs.
