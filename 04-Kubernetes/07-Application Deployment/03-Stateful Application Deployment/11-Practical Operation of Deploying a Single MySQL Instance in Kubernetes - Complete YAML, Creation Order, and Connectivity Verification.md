## I. Practical Objectives

The goal of this section is to complete a basic deployment of a single MySQL instance and verify the following:

- The MySQL Pod can start normally
- The root password is injected through a Secret
- MySQL configuration is mounted using a ConfigMap
- The data directory is persisted using a PVC
- Business services can access MySQL through a Service
- Data is retained after the Pod is recreated

The focus of this section is to establish a minimal, understandable, executable, and verifiable basic deployment model for MySQL, without covering more complex topics such as master-slave setups, high availability, or automatic failover.

## IV. Create a Secret: Store the root Password

### File: `01-secret.yaml`

    apiVersion: v1
    kind: Secret
    metadata:
      name: mysql-secret
    type: Opaque
    stringData:
      MYSQL_ROOT_PASSWORD: StrongPass123!

### Explanation

This Secret serves only one purpose:

- To store the root password

The `stringData` format is used here for ease of testing with a fixed value.  
In a real production environment, passwords should be generated and managed through secure processes, and it is not recommended to use the fixed password from this example for long-term use.

## V. Create a ConfigMap: Store MySQL Configuration

### File: `02-configmap.yaml`

    apiVersion: v1
    kind: ConfigMap
    metadata:
      name: mysql-config
    data:
      my.cnf: |
        [mysqld]
        character-set-server=utf8mb4
        collation-server=utf8mb4_general_ci
        max_connections=200
        default-authentication-plugin=mysql_native_password

### Explanation

This ConfigMap is used to provide MySQL with a basic configuration file.

The parameters in this example serve the following purposes:

- `character-set-server=utf8mb4`  
  Sets the default character set for the server.

- `collation-server=utf8mb4_general_ci`  
  Sets the default collation rule.

- `max_connections=200`  
  Sets the maximum number of connections allowed.

- `default-authentication-plugin=mysql_native_password`  
  Ensures compatibility with some older clients or applications that use traditional authentication methods.

This section does not delve into detailed MySQL parameter tuning; the focus is on establishing the practice of externalizing configuration files.

## VI. Create a Service: Provide a Stable Access Point

### File: `03-service.yaml`

    apiVersion: v1
    kind: Service
    metadata:
      name: mysql
    spec:
      selector:
        app: mysql
      ports:
        - port: 3306
          targetPort: 3306

### Explanation

The purpose of this Service is:

- To provide a stable access point for MySQL
- To hide theIn this single-instance model, the focus is on establishing a stable access point, rather than member-level discovery.`kubectl get svc mysql` returns normal results, but `mysql -h mysql -uroot -p` fails to establish a connection.

### Troubleshooting Directions

#### 1. Check if the Service selector matches the Pod labels

    kubectl get pod --show-labels
    kubectl get svc mysql -o yaml

Confirm that:
- The Service selector is `app: mysql`
- The Pod labels are `app: mysql`

#### 2. Verify if the MySQL Pod is Ready

    kubectl get pod mysql-0

#### 3. Check if port 3306 is listening inside the container

    kubectl exec -it mysql-0 -- sh

From within the container, you can check the status of the MySQL process and ports.

## Issue 20: ConfigMap Changes Not Taking Effect

### Reason
MySQL typically reads its configuration files during startup.  
Even if the contents of the ConfigMap are updated, the MySQL process will not automatically reload all configurations.

### Solution
You usually need to restart the Pod for MySQL to reload the new configuration:

    kubectl delete pod mysql-0

### Note
Before restarting, make sure the configuration file content is correct to avoid startup failures due to incorrect settings.

## Issue 21: Exposing a Database Directly as a Regular Service

### Explanation
MySQL should not be exposed directly via NodePort or LoadBalancer by default.  
More common practices include:

- Using a ClusterIP Service for internal cluster access
- Using port forwarding for administrative or debugging purposes

### Example of Temporary Port Forwarding

    kubectl port-forward svc/mysql 3306:3306

Then, you can access it locally using:

    mysql -h 127.0.0.1 -P 3306 -uroot -p

This method is suitable for learning environments and temporary troubleshooting.

## Issue 23: Summary of This Phase

This practical guide on deploying a single MySQL instance demonstrates a fundamental database deployment framework in Kubernetes:

- StatefulSet manages the running instance
- PVC stores persistent data
- ConfigMap provides external configuration
- Secret manages sensitive credentials
- Service ensures stable access

Through this example, you should understand the following key points:

- The MySQL data directory must be persistent.
- Database configurations should be externalized.
- Secrets should not be stored in workloads in plaintext.
- Services should be used for access rather than Pod IPs.
- After rebuilding a Pod, verify that data is intact.

Although this model is basic, it demonstrates the minimal viable form of a stateful application in Kubernetes.

## Key Terms Summary

- StatefulSet: The stateful container for hosting MySQL
- PVC: The persistent volume for storing MySQL data
- ConfigMap: The external configuration object for MySQL
- Secret: The object for managing MySQL passwords securely
- Service: The stable access point for MySQL services
- `/var/lib/mysql`: Common MySQL data directory
- `/etc/mysql/conf.d`: Common MySQL configuration directory
- `mysql:3306`: Common port for accessing MySQL within the cluster

## Additional Operational Insights

Deploying a single MySQL instance in Kubernetes is a good practice for learning containerization. The key to successful deployment lies in clearly defining the responsibilities of each component:

- Data should be stored separately from configuration.
- Secrets should be managed securely.
- Access should be controlled through Services rather than Pod IPs.
- Workloads should be designed with clear roles.

Once these principles are understood, you can move on to more advanced topics such as initialization and recovery, monitoring, backup and recovery, using Helm or Operators, and managing more complex database setups. These will help you build a solid foundation in Kubernetes operations.
