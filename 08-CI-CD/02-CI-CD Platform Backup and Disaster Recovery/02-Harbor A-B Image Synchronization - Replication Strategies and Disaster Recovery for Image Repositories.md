## I. Document Overview

Harbor is a commonly used container image repository within enterprises, primarily for storing images generated by CI/CD pipelines.

In a typical Kubernetes application delivery process, Harbor sits between Jenkins/GitLab CI and the Kubernetes cluster:

    GitLab Code Repository
       |
       v
    Jenkins / GitLab CI
       |
       v
    Build Container Images
       |
       v
    Push to Harbor
       |
       v
    Kubernetes Pulls Images from Harbor
       |
       v
    Pods Launch Application Containers

If Harbor fails, the consequences are not limited to "inability to push images"; it may also lead to:

- New versions cannot be released
- Pod reconstruction fails to pull images
- Deployment scaling out encounters issues
- Business continuity is disrupted after node reconfiguration
- Historical images cannot be retrieved during rollbacks
- Disaster recovery clusters lack necessary images
- CI/CD release processes are interrupted

Therefore, in production environments, Harbor image repositories must consider synchronization, backup, recovery, and disaster recovery capabilities.

This document uses Harbor A and Harbor B as examples to explain the basic principles of Harbor Replication strategies, Web UI configuration methods, verification approaches, common troubleshooting, and best practices for production use.

## II. Why Harbor A/B Image Synchronization is Needed

### 2.1 Risks of Using a Single Harbor

If an enterprise relies on only one Harbor, potential risks include:

- Harbor server failures
- Storage corruption
- Database errors
- Upgrade failures
- Certificate issues
- Network unavailability
- Data center failures
- Accidental deletion of projects or images
- Misconfigured garbage collection or retention policies leading to the loss of critical images
- Permission configuration errors causing inaccessible images

For Kubernetes, an unavailable image repository may not immediately affect running Pods but can cause problems when images need to be re-pulled:

    1. Pod redeployment after deletion
    2. Pod drift after node failure
    3. Deployment scaling
    4. Rolling updates
    5. New nodes joining the cluster
    6. Local image cache clearance
    7. Business version rollbacks

If a node lacks local image caches and Harbor is unavailable, issues such as ImagePullBackOff, ErrImagePull, and Back-off pulling images may occur.

### 2.2 Value of A/B Image Synchronization

The core benefits of Harbor A/B synchronization include:

- Redundancy of image assets
- Support for disaster recovery
- Multiple clusters can pull images simultaneously
- Cross-datacenter image distribution
- Image transfer between testing and production environments
- Offline synchronization in preparation for disasters
- Reduction of the impact of single-point failures in Harbor
- Increased reliability of the image release process

## III. What is Harbor Replication?

Harbor Replication is an integrated image replication feature within Harbor itself.

It does not involve simple rsync operations at the operating system level or direct copying of the database. Instead, it uses Harbor’s own replication rules to synchronize resources such as images, Tags, and Artifacts from one repository to another.

Replication can be used for:

- Between two Harbor repositories
- From a Harbor repository to a non-Harbor registry
- From a non-Harbor registry to a Harbor repository
- From a local Harbor to a cloud provider’s image repository
- From a cloud provider’s image repository to a local Harbor
- Cross-datacenter, cross-environment, and cross-cluster image distribution

Common usage scenarios:

    Harbor A ---- Push-based Replication ----> Harbor B

or:

    Harbor B ---- Pull-based Replication ----> Harbor A

In enterprise A/B image synchronization, the most common approach is to configure Push-based Replication in Harbor A to automatically push images to Harbor B.

### 7.6 How to Choose Trigger Mode

There are three common trigger methods for Harbor Replication:

| Trigger Method | Meaning | Usage Scenarios |
|---|---|---|
| Manual | Manually execute synchronization | Initial synchronization, supplementary synchronization |
| Scheduled | Synchronize at regular intervals | Nighttime batch synchronization, off-peak synchronization across data centers |
| Event Based | Synchronize triggered by events | Automatic synchronization after image push |

If the requirement is:

    After pushing to Harbor A, Harbor B should synchronize automatically

Then choose:

    Event Based

This is the most critical "automatic synchronization switch" in the Web UI.

---

### 7.7 How to Write Name Filter

Name Filter is used to control which repositories are synchronized.

Common examples:

| Rule | Explanation |
|---|---|
| devops/** | Synchronize all images under the devops project |
| devops/demo-app | Only synchronize devops/demo-app |
| middleware/** | Synchronize all images under the middleware project |
| ** | Synchronize all projects; use with caution in production |

If the image address is:

    harbor-a.example.com/devops/demo-app:v1.0.0

You can configure it as:

    devops/demo-app

Or to synchronize the entire project:

    devops**

---

### 7.8 How to Write Tag Filter

Tag Filter is used to control which image versions are synchronized.

Common examples:

| Rule | Explanation |
|---|---|
| v* | Synchronize versions starting with v |
| release-* | Synchronize versions starting with release |
| prod-* | Synchronize versions starting with prod |
| * | Synchronize all Tags |
| latest | Only synchronize the latest version; not recommended for production |

In production, it is recommended to synchronize traceable version tags, such as:

    v1.0.0
    release-20260428-001
    main-a1b2c3d-1024

It is not recommended to rely solely on:

    latest

---

### 7.9 Whether to Enable Override

Override indicates whether to overwrite existing images with the same name and Tag in the target Harbor B.

Production recommendations:

    It is generally not recommended to enable Override.
    Use immutable Tags to manage versions.

Reasons:

    Repeated overwriting of the same Tag can make it difficult to track changes between repositories A and B.
    It also hinders rollback and auditing processes.

In testing environments where the latest version is frequently used, Override can be enabled as needed.

---

### 7.10 Whether to Enable Delete Synchronization

"Delete remote resources when locally deleted" means that when an image is deleted in Harbor A, it should also be deleted in Harbor B.

This option is not recommended for disaster recovery scenarios.

Reasons:

    If a production image is accidentally deleted in Harbor A, it will also be deleted from Harbor B.
    This would result in the disaster recovery repository losing its protective function.

Recommended strategy:

    New additions and updates can be synchronized.
    Deletion actions should not be easily replicated to the disaster recovery repository.

## Section Eleven: Scheduled Synchronization Strategy

If you don't want images to be synchronized immediately after each push, you can use Scheduled synchronization.

Use cases:

- Limited bandwidth across regions
- Lower synchronization costs at night
- Approximate synchronization for disaster recovery repositories
- Large number of images that shouldn't affect daily releases
- Clear synchronization windows between test and production repositories

Example strategies:

| Scenario | Cron |
|---|---|
| Every 2 AM | 0 2 * * * |
| Every 6 hours | 0 */6 * * * |
| Every 3 AM every week | 0 3 * * 0 |

Note:

    Scheduled synchronization reduces real-time performance.
    If RPO requirements are very low, you should choose Event-Based or more frequent synchronization.

## Section Twelve: Differences Between A/B Synchronization and Harbor Backup

Harbor Replication is not the same as a full backup of Harbor.

### 12.1 What Replication Can Achieve

Replication mainly solves:

- Image replication
- Artifact synchronization
- Tag synchronization
- Cross-repository distribution
- Redundancy of master-slave repository images
- Advance retention of image artifacts for disaster recovery repositories

---

### 12.2 What Replication Cannot Replace Completely

Replication cannot completely replace:

- Harbor database backups
- Harbor configuration backups
- User permission backups
- Project metadata backups
- Robot Account backups
- Scan report backups
- Audit log backups
- System configuration backups
- Certificate backups
- Storage backend backups

For example:

    Harbor A contains project permissions, users, Robot Accounts, scan policies, retention policies, and Webhook configurations.
    Replication mainly synchronizes image resources; it does not mean that these management configurations are fully replicated.

Therefore, production disaster recovery should have two layers:

    First layer: Replication ensures that image assets exist in Harbor B.

### 14.3 Failure in Replication Execution: forbidden

Possible causes:

- The Robot Account only has pull permissions and no push permissions.
- Insufficient permissions for the target project.
- The current account is not allowed to push to the target project.
- The account's scope does not include the target Project.

Actions to take:

    1. Check the permissions of the Robot Account on Harbor B.
    2. Ensure that the Repository Push permissions are available.
    3. Verify that the target Project is set to devops mode.
    4. Regenerate the Token and update the Endpoint accordingly.

---

### 14.4 Failure in Replication Execution: project not found

Possible causes:

- The corresponding Project does not exist on Harbor B.
- Incorrect configuration of the Destination Namespace.
- Inconsistent naming between the source and target projects.
- Issues with path formation due to Flattening.

Actions to take:

    1. Create the target Project on Harbor B.
    2. Check the settings for the Destination Namespace.
    3. Verify the Name Filter configuration.
    4. Adjust the Destination Flattening settings.
    5. Retry the synchronization process.

---

### 14.5 Synchronization Successful, but Images Cannot be Found in Harbor B

Possible causes:

- The images were synchronized to a different Namespace.
- Flattening changed the path of the images.
- The Tag filtering rules did not match the actual images.
- Only certain types of resources were synchronized due to Resource filtering settings.
- The incorrect project or repository was selected.

Actions to take:

    1. Check the Replication task logs for any errors.
    2. Verify the Target Namespace to ensure the images are stored there.
    3. Search for the image names in Harbor B.
    4. Adjust the Destination Flattening settings if necessary.
    5. Try manually pulling the images using docker pull.

---

### 14.6 Event Based Triggering Does Not Occur Automatically

Possible causes:

- The Trigger Mode is not set to Event Based.
- The pushed images do not match the filtering rules.
- The Tags used do not match.
- The images were pushed to a different Project.
- The relevant rules have been disabled.
- Issues with the JobService or the internal task queue in Harbor A.

Actions to take:

    1. Verify whether the Replication Rule is enabled.
    2. Check the Name Filter and Tag Filter settings.
    3. Monitor the status of the JobService.
    4. Review the Replication Execution logs for any errors.
    5. Check the Harbor logs for related issues.

For Docker Compose deployments, check the logs using:

    docker compose logs -f jobservice
    docker compose logs -f core

For Kubernetes deployments, check the logs using:

    kubectl logs -n harbor deploy/harbor-jobservice
    kubectl logs -n harbor deploy/harbor-core

---

### 14.7 Slow Image Synchronization

Possible causes:

- The image size is very large.
- Insufficient cross-datacenter bandwidth.
- Excessive concurrent synchronization requests.
- Slow storage performance on the target Harbor.
- Network fluctuations.
- Insufficient resources for the Harbor JobService.
- Poor storage performance of the Registry backend.

Optimization suggestions:

    1. Reduce the size of the images.
    2. Avoid rebuilding large base layers repeatedly.
    3. Set appropriate synchronization time windows.
    4. Schedule synchronization tasks during off-peak hours.
    5. Adjust bandwidth limits as needed.
    6. Optimize the storage performance of Harbor.
    7. Increase resources allocated to the JobService.
    8. Preheat base images in advance.

---

### 14.8 Failure in Pulling Images from Harbor B

Possible causes:

- The image synchronization was not successful.
- Incorrect configuration of the imagePullSecret.
- The Kubernetes node does not trust the certificate provided by Harbor B.
- Using an HTTP repository but containerd/Docker is not configured to use insecure registries.
- Incorrect image address specified.
- Insufficient permissions for the Harbor B account.

Actions to take:

    Use the following commands to check the node status and image pull attempts:

    kubectl describe pod <pod-name> -n <namespace>
    kubectl get events -n <namespace> --sort-by=.lastTimestamp

    On the node, try pulling the image using either:

    crictl pull harbor-b.example.com/devops/nginx:v1.0.0

    or

    ctr -n k8s.io images pull harbor-b.example.com/devops/nginx:v1.0.0

## XVII. Interview Answer Guidelines

If you are asked in an interview:

    There are two Harbors, Harbor A and Harbor B. How can images pushed to Harbor A be automatically synchronized to Harbor B?

You can answer as follows:

    This is typically achieved using Harbor's built-in Replication feature; it is not recommended to directly use rsync to copy the data directories between the two Harbors. The process involves creating a target Project and a dedicated Robot Account on Harbor B, granting this Account push/pull permissions for the target project. Then, in Harbor A's Web UI, go to Administration -> Registries, create a Replication Endpoint pointing to Harbor B, and provide the necessary information such as Harbor B's address, Robot Account, and Token. After verifying that the Endpoint connection is successful, proceed to Administration -> Replications to create a Replication Rule. Set the rule to be Push-based, select Harbor B as the Destination Registry, use Name Filter to control which projects or repositories are synchronized (e.g., devops/**), and Tag Filter to specify which versions (e.g., v* or release-*) should be synced. If you want automatic synchronization after pushing to Harbor A, set the Trigger Mode to Event Based. This way, when CI/CD pushes an image to Harbor A, Harbor A will automatically trigger the replication task to sync the matching images to Harbor B. After synchronization, verify that the images and Tags exist on Harbor B and test them using docker pull or Kubernetes Pods. In production environments, pay attention to certificate management, network settings, firewall configurations, ensuring minimal permissions for the Robot Account, keeping Tags immutable, being cautious when enabling image deletion synchronization, and recognizing that Harbor B is not a complete backup solution. Replication primarily serves to reduce redundancy of image assets; Harbor's database, configuration, certificates, and metadata should still be backed up separately.

## XIX. Avoid Confusing Replication with High-Availability Clusters

Harbor A/B Replication is more akin to:

    Data synchronization and disaster recovery at the image repository level

It is not equivalent to:

    High-availability clusters for Harbor

The differences between them are as follows:

| Type | Description |
|---------|--------------------------|
| Replication | Image replication between two Harbor instances |
| HA | Multiple copies of Harbor components providing a single service entrance |
| Backup and Recovery | Complete capability to restore databases, configurations, storage, certificates, etc. |
| Registry Mirror | Cache or proxy for image pulls |
| Proxy Cache | Caches images from remote repositories |
