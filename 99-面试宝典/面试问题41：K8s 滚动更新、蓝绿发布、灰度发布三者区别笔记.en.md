# 一、先记一句总概括

These three methods are essentially **application deployment strategies**, with the following differences:

- **Rolling Update**: Old version Pods are replaced by new ones in batches.
- **Blue-Green Deployment**: Two identical environments are prepared, and traffic is switched from the old to the new version at once.
- **Canary Release**: Both old and new versions are online simultaneously; initially, only a portion of traffic is directed to the new version, which is then gradually increased.

# 二、What is Rolling Update

## 1. Definition
Rolling Update is the most common deployment method in Kubernetes by default.

Its core concept is:

**Instead of deleting all old Pods and creating new ones at once, new Pods are created while old ones are deleted, allowing for a gradual replacement of versions.**

## 2. Example
Suppose a Deployment currently has 4 v1 Pods. When upgrading to v2, Kubernetes might proceed as follows:
- Create 1 new v2 Pod.
- Delete 1 old v1 Pod.
- Create another new v2 Pod.
- Delete another old v1 Pod.

This process continues until all Pods have been replaced.

## 3. Advantages
- **Natively supported**: The simplest and most straightforward method.
- **No need for two complete environments**.
- **Business continuity during deployment**.
- **Relatively low resource consumption**.

## 4. Disadvantages
- **Temporary coexistence of old and new versions**.
- **Potential for wider impact if issues arise with the new version**.
- **Less straightforward rollback compared to Blue-Green Deployment**.
- **Not suitable for highly complex compatibility scenarios**.

## 5. How Kubernetes Implements it
This is mainly achieved through:

- The `Deployment` resource.
- The `strategy.type: RollingUpdate` configuration option.
- Parameters such as:
  - `maxUnavailable`: The maximum number of old Pods allowed to be unavailable during the upgrade process.
  - `maxSurge`: The maximum number of additional new Pods that can be created compared to the desired total.

For example:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 1  
```

### Parameter Explanation

- `maxUnavailable`: Indicates how many old Pods can be unavailable at any given time during the upgrade.
- `maxSurge`: Specifies the maximum additional number of new Pods that can be created compared to the desired total.

# 三、What is Blue-Green Deployment

## 1. Definition
Blue-Green Deployment involves preparing two nearly identical environments: one for running the old version and the other for the new version. Once the new version has been tested and verified, traffic is switched from the old environment to the new one in a single step.

Common terms used are:

- **Blue**: The old version.
- **Green**: The new version.

## 2. Example
Suppose the current production environment uses v1 (blue). To deploy v2 (green), you first create a new environment for it but do not let any traffic flow through it yet. After thorough testing, you configure a `Service` or `Ingress` to direct all traffic from the production environment to the new green environment. If any issues arise during this transition, you can quickly switch back to the blue environment.

## 3. Advantages
- **Fast switching**: Both deployment and rollback processes are quick.
- **High risk control**: Issues with the new version can be identified and resolved promptly.
- **Complete environment verification before deployment**: All components of the new environment can be tested thoroughly before going live.

## 4. Disadvantages
- **Higher resource costs**: Two complete environments need to be maintained.
- **Additional complexity in infrastructure management**: Managing both environments requires extra effort.
- **Special attention required for database and configuration changes**: Any modifications to these systems must be carefully coordinated between the two environments.

## 5. How Kubernetes Implements it
In Kubernetes, Blue-Green Deployment is typically achieved by combining the following components:

- Two `Deployment` resources for the old and new versions.
- A `Service` or `Ingress` that directs traffic between the environments.
- In more advanced scenarios, tools like **Argo Rollouts**, **Istio**, or **Helm** can be used to simplify the deployment process.

## 6. Common Implementation Approaches

### Method One: Service-Based Switching
For example:

- `myapp-v1` Deployment for the old version.
- `myapp-v2` Deployment for the new version.

Initially, the `Service` selects the v1 Deployment:

```yaml
selector:
  app: myapp
  version: v1
```

After the upgrade, it is changed to select the v2 Deployment:

```yaml
selector:
  app: myapp
  version: v2
```
