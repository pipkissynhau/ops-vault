# 4.11 - Monitoring System Interview Notes

## Document Description
This document is used to address basic monitoring-related questions in interviews for operations/operations quality management/platform operations, with the focus not on deep architecture design but helping to quickly explain:
1. Monitoring layered thinking
2. Responsibilities of common Prometheus ecosystem components
3. Differences between Kubernetes and business monitoring
4. Monitoring perspective in multi-business shared clusters
5. Safe, non-overblown expression methods in interviews

## I. Don't Answer Monitoring as 'A Tool', but as a 'Layered System'

In interviews, don't start by only mentioning Prometheus, Grafana. First explain the monitoring layered system.

### 1. Infrastructure Layer
Monitoring Objects:
- Physical Machines
- Virtual Machines
- Linux Hosts
- CPU
- Memory
- Disk
- Network
- inode
- load

Common Components:
- node-exporter

Answer Focus:
- This layer mainly checks if machine resources are healthy
- Used to determine if there are resource bottlenecks in the host
- Common issues like high CPU, memory shortage, disk full, network anomalies

### 2. Kubernetes Platform Layer
Monitoring Objects:
- Node
- Pod
- Deployment
- StatefulSet
- DaemonSet
- PVC / PV
- HPA
- Container CPU / Memory
- Pod Restarts
- Scheduling Status

Common Components:
- kube-state-metrics
- cAdvisor
- kubelet metrics

Answer Focus:
- This layer mainly checks the status of K8s resource objects and container runtime status
- Used to determine if the issue is platform layer or business itself

### 3. Middleware Layer
Monitoring Objects:
- MySQL
- Redis
- Kafka
- Nginx
- Elasticsearch

Common Components:
- mysqld-exporter
- redis-exporter
- kafka-exporter
- nginx exporter

Answer Focus:
- This layer mainly checks the status of components themselves
- For example, connection counts, latency, slow queries, consumption backlog, master-slave status, etc.

### 4. Business Application Layer
Monitoring Objects:
- Interface Success Rate
- Response Time
- Error Rate
- Core Chain
- SLA / SLO
- Whether users can actually use the business

Common Methods:
- Applications exposing /metrics themselves
- blackbox-exporter
- Log Analysis
- Trace Tracking

Answer Focus:
- This layer truly reflects business availability
- Pod normal doesn't mean business is necessarily normal
- Business monitoring can't be replaced by K8s resource monitoring alone

## II. Responsibilities of Common Prometheus Ecosystem Components

### 1. Prometheus
Role:
- Responsible for scraping metrics
- Responsible for storing time-series metrics
- Responsible for PromQL queries
- Provides data source for alerts and visualization

One-sentence Memory:
- Prometheus is responsible for collection and storage

### 2. Grafana
Role:
- Responsible for dashboard visualization
- Responsible for multi-dimensional filtering and visualization
- Responsible for organizing dashboards by team, business, and theme

One-sentence Memory:
- Grafana is responsible for visualization

### 3. Alertmanager
Role:
- Responsible for receiving Prometheus alerts
- Responsible for alert grouping, routing, suppression, and notification
- Integrates with enterprise WeChat, Feishu, Webhook, email, etc.

One-sentence Memory:
- Alertmanager is responsible for alert notifications

### 4. node-exporter
Role:
- Collects node-level metrics
- For example, CPU, memory, disk, network

One-sentence Memory:
- node-exporter monitors machines

### 5. kube-state-metrics
Role:
- Collects Kubernetes resource object status
- For example, Pod, Deployment, Node, PVC, HPA status

One-sentence Memory:
- kube-state-metrics monitors K8s object status

### 6. cAdvisor
Role:
- Provides container resource usage
- For example, container CPU, memory, filesystem, network traffic

One-sentence Memory:
- cAdvisor monitors container resources

### 7. mysqld-exporter
Role:
- Connects to MySQL
- Collects MySQL metrics
- Exposes metrics for Prometheus scraping

One-sentence Memory:
- mysqld-exporter monitors MySQL

### 8. blackbox-exporter
Role:
- Performs black-box probing
- Checks HTTP, TCP, ICMP reachability and response status

One-sentence Memory:
- blackbox-exporter performs probing from the user access perspective

## III. What is kube-state-metrics

### Standard Understanding
kube-state-metrics is mainly used to convert Kubernetes API resource object status into metrics that Prometheus can scrape.

### What It Monitors
- Whether Pod is Running / Pending / Failed
- Whether Deployment desired replicas match available replicas
- Whether Node is Ready
- Whether PVC is Bound
- Whether StatefulSet / DaemonSet status is normal
- HPA current replica count, target replica count

### What It Does Not Monitor
It does not directly monitor:
- Host CPU, memory, disk
- Business interface success rate
- MySQL connection count
- Java JVM metrics
- User transaction success rate

### Interview Standard Answer
kube-state-metrics mainly collects Kubernetes resource object status, such as Pod, Deployment, Node, PVC, HPA, etc. It leans more toward platform resource layer and orchestration layer monitoring, and does not directly reflect whether business interfaces are normal.

## IV. kube-state-metrics Monitors K8s Resources, Not Business Itself

This question is often asked.

### You Can Understand It This Way
kube-state-metrics monitors not "whether the business is truly available", but "whether the K8s resource object status that the business depends on is normal".

For example:
- Whether Pod is running
- Whether replicas are sufficient
- Whether nodes are normal
- Whether PVC is successfully bound

### Typical Scenario
A Java service may:
- Pod Running
- Deployment normal
- Service normal

But the business may still have issues:
- Interface 500
- Slow response
- Database connection pool exhausted
- Downstream service anomalies

Therefore:
- K8s resources normal ≠ business normal
- Pod normal ≠ service necessarily normal

## V. How to Monitor Business Pod, Taking MySQL as an Example

### MySQL Cannot Be Monitored Only by Pod
MySQL business Pod cannot be monitored only by:
- Whether Pod is Running
- Whether StatefulSet is normal
- Whether PVC is bound

You also need to monitor MySQL's own business metrics.

### Four-Layer Monitoring Approach for MySQL

#### 1. Node Layer
See:
- Node CPU
- Node Memory
- Disk
- Network
- IO

Components:
- node-exporter

#### 2. Container / Pod Layer
See:
- Pod CPU / Memory
- Container restart count
- OOMKilled
- Container filesystem usage

Components:
- cAdvisor
- kubelet metrics

#### 3. K8s Object Layer
See:
- Pod status
- StatefulSet status
- PVC status
- Node Ready status

Components:
- kube-state-metrics

#### 4. MySQL Business Layer
See:
- Whether MySQL is reachable
- Connection count
- QPS / TPS
- Slow queries
- Lock wait
- Master-slave delay
- InnoDB Buffer Pool
- Deadlocks
- Tablespace / Data directory capacity

Components:
- mysqld-exporter

### Interview Standard Answer
MySQL business Pods cannot only monitor Kubernetes layer, but need layered monitoring. Node layer monitors host resources, container layer monitors Pod CPU, memory and restart status, Kubernetes layer monitors Pod, StatefulSet, PVC status, business layer uses mysqld-exporter to collect MySQL own metrics, such as connection count, slow queries, QPS, TPS, master-slave delay, etc.

## SixI don't know.Understanding MySQL Monitoring Chain

### Simplest Monitoring Chain
Prometheus --> mysqld-exporter --> MySQL

### Meaning
- MySQL is the monitored object
- mysqld-exporter is responsible for connecting to MySQL and reading status
- Prometheus scrapes metrics exposed by mysqld-exporter
- Grafana displays metrics
- Alertmanager handles alerts

### Simplest Implementation Order
1. Start MySQL StatefulSet first
2. Ensure MySQL can login and access normally
3. Deploy mysqld-exporter
4. Verify /metrics endpoint is normal
5. Let Prometheus scrape it

### Interview Answer
Usually, we first ensure MySQL itself runs normally in K8s, then deploy mysqld-exporter separately to connect this MySQL, exposing MySQL own metrics to Prometheus.

## SevenI don't know.Should Business Monitoring and Infrastructure Monitoring be on the same platform

### Recommended Answer
In production, it's usually recommended to place them on the same monitoring platform system, for unified collection, display, alerting and fault correlation analysis, but cannot mix into a single view.

### Correct Understanding
- Platform can be unified
- View must be layered
- Alerts should be graded
- Responsibility boundaries must be clear

### Why Unified Platform
Benefits:
- More complete troubleshooting chain
- Easier alert correlation
- Operations, platform, and R&D teams can view issues in the same system
- From business anomalies, can trace down to platform layer and resource layer

### Why Not Fully Mixed
Because:
- Business teams care about interface success rate, RT, error rate
- Platform teams care about Pod, Node, PVC, node resources
- Middleware teams care about MySQL, Redis, Kafka own status

### Interview Standard Answer
Infrastructure monitoring and business monitoring are generally recommended to be on the same platform system, but display and usage must be layered. Infrastructure layer views clusters and nodes, platform layer views K8s resources, business layer views interface and service metrics. This enables unified troubleshooting chain while avoiding view confusion.

## EightI don't know.Will There Be Many Grafana Dashboards

### Standard Understanding
There will be multiple dashboards, but should not let on-call people search through a large number of dashboards randomly.

### More Reasonable Structure
Generally divided into three layers:

#### 1. Overview Dashboard
See:
- Cluster health
- Core business health
- Total alert count
- Core resource trends

Purpose:
- Quickly determine where the problem is

#### 2. Topic Dashboard
Examples:
- Node resource dashboard
- K8s workload dashboard
- MySQL dashboard
- Redis dashboard
- Ingress dashboard

Purpose:
- Deep dive into a specific layer

#### 3. Service Dashboard
Examples:
- A business application dashboard
- A middleware instance dashboard

Purpose:
- For specific business teams or component owners

### Key Points
Not every object needs a separate dashboard. Many dashboards are templated and switched via variables:
- cluster
- namespace
- app
- workload
- pod
- instance

### Interview Answer
In production, there will be multiple dashboards, but generally designed into three-level structure: overview dashboard, topic dashboard, and service dashboard. Combined with variable and alert jump links, reduce manual page switching costs.

## NineI don't know.What to Do When Multiple Businesses Share One K8s Cluster

### This is a very common scenario
A cluster may run:
- User system
- Order system
- Payment system
- Risk control system
- Internal system
- Middleware

### Monitoring Platform Approach
Usually still unified platform, but split via these dimensions:
- namespace
- app
- team
- env
- service
- owner

### Infrastructure Layer
View globally:
- Nodes
- Cluster resources
- Overall Pod status
- kubelet / scheduler / etcd etc.

### Platform Layer
Support drilling by namespace / workload / app

### Business Layer
Must split by business:
- A business views A's interface, success rate, error rate
- B business views B's core chain

### Interview Standard Answer
Multiple businesses sharing one K8s cluster is common. Monitoring platform is usually unified, but split via namespace, labels, environment, and responsibility team. Infrastructure and cluster level view globally, business level view dashboard and alerts by specific business.

## TenI don't know.Does Prometheus Have a Multi-Tenant System

### Conclusion
Prometheus itself is not a complete multi-tenant permission platform.

### More Accurately
Prometheus native is more biased toward:
- Metric collection
- Time series storage
- Query

Not specifically for:
- A user only sees A business
- B user only sees B business
- Strict business-level permission isolation

### Production Approach
Usually combined with Grafana for:
- User
- Team
- Folder
- Dashboard permission

Example:
- A team only sees A business folder
- B team only sees B business folder
- Platform team can see full cluster monitoring

### Interview Standard Answer
Prometheus native is more biased toward collection and storage, not a complete multi-tenant platform with business-level visibility isolation. In production, usually combined with Grafana for team, folder, and dashboard permission control to achieve A team sees A business, B team sees B business.

## ElevenI don't know.Safe Monitoring Expression Boundary in Interviews

This section is very important.

### What You Can Say: "Done / Exposed / Participated In" Content
- Participated in Prometheus + Grafana related work
- Exposed to node monitoring, K8s platform monitoring
- Understand the role of kube-state-metrics, node-exporter
- Participated in basic alert rule configuration
- Exposed to release support, deployment issue troubleshooting, monitoring viewing

### What You Can Say: "Understand / Have Basic Awareness" Content
- Business monitoring vs platform monitoring layering
- Monitoring perspective splitting in multi-business shared cluster
- Basic pipeline of mysqld-exporter
- Grafana dashboard organization by business logic

### What You Should NOT Say: "Led" Content
- Complete monitoring platform architecture design
- Monitoring permission system design
- Multi-tenant monitoring governance
- Mature alert platform governance
- Complete business observability system owner

### Core Principles
Say "participated in" when you participated in, say "understood" when you understood. Do not claim ownership of content beyond your boundary.

## Twelve. Monitoring Interview Universal Answer Template

The following can be memorized directly.

I understand production monitoring isn't a single layer, but layered construction. Infrastructure layer mainly monitors hosts and resources, such as CPU, memory, disk and network; Kubernetes platform layer mainly monitors Pod, Deployment, Node, PVC resource object status and container resource usage; middleware layer monitors MySQL, Redis, Kafka and other components' own metrics; business layer further monitors interface success rate, response time and error rate. Prometheus mainly handles metric collection and storage, Grafana handles visualization, Alertmanager handles alerts. When issues occur, you can trace from business anomalies down to platform layer and infrastructure layer.
