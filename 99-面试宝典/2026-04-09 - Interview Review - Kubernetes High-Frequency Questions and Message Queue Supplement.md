## 1. Pod Creation Process

### Interview Question
What is the process of creating a Pod?

### What This Question Truly Tests
1. Whether you understand the full chain from YAML to Running for a Pod  
2. Whether you can distinguish responsibilities between control plane and node side  
3. Whether you have a troubleshooting perspective, rather than just reciting standard answers  

### More Stable Answering Approach
When answering this type of question, don't start by reciting:
- apiserver
- etcd
- scheduler
- kubelet
- runtime
- CNI

A better approach is to first present your own understanding framework:

> I generally divide the Pod creation process into four stages: **Object entering the cluster, completing scheduling, node execution creation, and status reporting**.

### Standard Answer (Interview Version)
I generally divide the Pod creation process into four stages: **Object entering the cluster, completing scheduling, node execution creation, and status reporting**.

First, the user submits the Pod YAML to apiserver, which performs authorization and validation checks. If there are no issues, it writes the Pod object to etcd. At this point, the Pod hasn't truly started running; it's just that the cluster has received this expected state.

Next, the scheduler looks at these unbound Pods, selects an appropriate node based on resource availability, node selection conditions, affinity, and taint tolerance strategies, and completes the binding.

After binding, the kubelet on the target node detects that this Pod should be created on this machine, then calls the container runtime to pull the image, create the pause container and business container. During this process, it also handles networking and storage, such as using CNI to configure Pod network settings and mounting volumes according to the definition.

After the container starts, the kubelet continuously reports the Pod's status back to apiserver, so we finally see the Pod transition from Pending to Running.

### Troubleshooting Perspective Supplement
From a troubleshooting perspective, the phenomena differ depending on which stage the issue occurs:

- If there's an issue during scheduling, the Pod usually remains **Pending**
- Image pull failure results in **ImagePullBackOff**
- Container startup failure commonly leads to **CrashLoopBackOff**

So, during troubleshooting, the essence is to determine where the Pod **gets stuck in the process**.

### This Question Review
This question isn't unknown, but it's easy to answer too template-like.  
In the future, pay attention to:
1. First explain your framework  
2. Then explain the chain  
3. Finally add a troubleshooting perspective

## 2. Will ipvs / iptables Rules Recover After Node Reboot?

### Interview Question
If the ipvs or iptables rules on a node are cleared, will they recover after rebooting the node?

### What This Question Truly Tests
1. Whether you know who generates the rules  
2. Whether you understand the rules are not manually maintained but dynamically synchronized by kube-proxy  
3. Whether you have a troubleshooting approach  

### Core Conclusion
**They will generally recover, but only if kube-proxy is functioning normally and the node can synchronize cluster state with apiserver after reboot.**

### Standard Answer (Interview Version)
This depends on the situation. Typically, the iptables or ipvs rules on a node are not manually maintained but are **dynamically generated by kube-proxy based on Service and Endpoint information**.

So if the rules are cleared, but kube-proxy is still running, it will have the opportunity to reapply them during synchronization. If the node reboots, as long as kube-proxy can start normally after the node recovers and can retrieve the current cluster's Service and Endpoint status from apiserver, these rules will generally be regenerated.

However, this isn't absolute. If kube-proxy isn't running, the node has communication issues with apiserver, the ipvs kernel module has problems, or the Service/Endpoint itself is abnormal, the rules may not recover, and business traffic will continue to be abnormal.

### Troubleshooting Supplement
When troubleshooting, I would first check:

1. Whether kube-proxy is functioning  
2. Whether the node is Ready  
3. `iptables -t nat -L -n` or `ipvsadm -Ln`  
4. Whether Service and Endpoints/EndpointSlice are normal  
5. Whether the node has normal connectivity with apiserver  

### This Question Review
When answering this question, don't just say "will recover" or "won't recover"—include the prerequisites.  
Key terms to remember:

- kube-proxy  
- Service  
- Endpoint  
- Dynamic synchronization  
- Conditional recovery  
- Troubleshooting approach

## 3. How to Migrate a Pod Created by Deployment to Another Node?

### Interview Question
After a Deployment creates a Pod, how can you migrate the Pod to another node?

### What This Question Truly Tests
1. Whether you know **Pods cannot be directly migrated**  
2. Whether you understand thatSo-called "migration" essentially means **rebuilding + rescheduling**  
3. Whether you know common practices in production environments  

### Core Conclusion
**Pods cannot be directly migrated.**  
If you want to have the Pod no longer run on the current node but instead run on another node, you essentially need to **modify scheduling constraints and rebuild the Pod** to achieve this.

### Standard Answer (Interview Version)
Strictly speaking from Kubernetes mechanisms, **Pods cannot be directly migrated to another node**.  
If the actual goal is to have this Deployment's Pod no longer run on the current node but instead run on another node, the usual approach is to modify scheduling constraints and combine it with rolling updates or node eviction to achieve this.

For example, a common practice is to first label the target node, then add `nodeSelector` or `nodeAffinity` in the Deployment's Pod template, then execute `rollout restart`, or trigger a rolling update by updating the Deployment, so the newly created Pods will be scheduled to the target node according to the new rules.

If you want to migrate all Pods on a node, you can also perform `cordon` or `drain` on the original node to make it unschedulable and evict existing Pods, and the controller will rebuild them on other nodes that meet the conditions.

### Production Environment Supplement
In actual operations, you also need to consider:

- Whether the business has multiple replicas  
- Whether there are PDBs  
- Whether local storage is used  
- Whether there are anti-affinity, taint tolerance, or other restrictions

### Review of This Question
I actually knew that **Pods cannot be directly migrated**, but during the interview I didn't first state this key definition, leading to losing the main point of the answer.

In the future, I should always follow this answering sequence:

1. **State the definition first**: Pods cannot be directly migrated  
2. **Explain the essence**: They can only be rebuilt and rescheduled  
3. **Discuss the methods**: nodeSelector / affinity / rollout restart / cordon / drain

# II. Supplementary Notes on Message Queues

---

## 1. What is a Message Queue

A message queue is essentially an **asynchronous communication mechanism**.  
Producers write messages to the queue first, and consumers then consume messages at their own pace.

### Common Uses
1. **Asynchronous Decoupling**  
   Frontend or upstream systems send messages and return immediately, without needing to wait for downstream processing to complete

2. **Traffic Smoothing**  
   Peak traffic is first accumulated in the queue, and the downstream processes it gradually

3. **Buffering Traffic Surges**  
   Prevents sudden requests from directly overwhelming databases, applications, and downstream services

4. **System Decoupling**  
   Systems communicate through messages rather than strong binding synchronous calls

### Interview Expression
The most common uses of message queues I understand are four: **asynchronous decoupling, traffic smoothing, traffic buffering, and system decoupling**.

---

## 2. Differences Between Redis and Kafka in Message Scenarios

### Redis
Redis is more commonly positioned as:
- Cache

It can also handle lightweight message scenarios, such as:
- List  
- Pub/Sub

However, it's usually not the first choice for many interviewers as a "professional MQ product".

### Kafka
Kafka is more standardly positioned as:
- Distributed message queue  
- Event stream platform  
- Log aggregation bus  
- Asynchronous decoupling middleware

### Interview Expression
Redis can handle lightweight message scenarios, but it's more oriented toward caching and high-performance data services. Kafka, on the other hand, is a more typical distributed message system, better suited for high-throughput, event stream, and log aggregation scenarios.

# III. Redis Cluster and Replication Mechanism

---

## 1. Two Common High Availability Architectures for Redis

### 1) Master-Slave + Sentinel
Features:
- Master node handles writes  
- Slave nodes replicate master data  
- Sentinel handles monitoring and failover  

Suitable for:
- High availability  
- Read-write separation  
- Medium to small scale deployments  

### 2) Redis Cluster
Features:
- Solves both high availability and data sharding  
- Data is not stored fully on all nodes, but split across different master nodes

---

## 2. Redis Cluster Principles

Redis Cluster divides the key space into **16384 hash slots**.  
When writing a key, it calculates which slot it belongs to using a hash algorithm, and writes it to the master node that manages that slot.

### Example
- master1 handles part of the slots  
- master2 handles part of the slots  
- master3 handles part of the slots  

Each master can also have replicas for redundancy.

### Interview Expression
The core of Redis Cluster is **sharding + replication**.  
It distributes data across multiple masters using 16384 hash slots, and each master has replicas for high availability, enabling horizontal scaling and failover when a master node fails.

---

## 3. Redis Replication Technology

### Redis Replication Fundamentals
Redis replication is essentially **master-slave replication**.

- Master node handles writes  
- Slave nodes replicate master data  

### Synchronization Methods
#### 1) Full Synchronization
Typically occurs when:
- A slave node connects to a master node for the first time  
- The master-slave difference is too large to perform incremental synchronization  

Process Understanding:
1. Slave node requests synchronization  
2. Master node generates RDB  
3. Sends RDB to the slave node  
4. Slave node loads RDB  
5. Sends write commands from the synchronization period to the slave node  

#### 2) Incremental Synchronization
If the master-slave has synchronized before, and the master node still retains data from the replication backlog buffer, only the differential part can be synchronized.

---

## 4. Significance of Redis Replication
1. High availability  
2. Data redundancy  
3. Read traffic expansion  

---

## 5. Limitations of Redis Replication
Redis replication defaults to **asynchronous replication**.  
That is, the master node's write success does not guarantee the slave node has fully synchronized.

Therefore, strictly speaking, Redis is not strongly consistent, and **some recently written data may be lost** during a master node failure switch.

### Interview Expression
Redis master-slave replication is more oriented toward eventual consistency rather than strong consistency. When a master node fails suddenly, there may be some recently written data that hasn't been synchronized to the slave nodes.

---

## 6. Redis Interview Quick Notes
- Redis master-slave replication achieves high availability  
- Master node handles writes, slave nodes replicate data  
- First synchronization is usually full synchronization, subsequent synchronizations are mostly incremental  
- Sentinel primarily solves monitoring and failover in master-slave architectures  
- Redis Cluster uses 16384 hash slots for data sharding  
- Each master can have replicas  
- Redis defaults to asynchronous replication, which may lose some recent data

# IV. Kafka Cluster and Replication Mechanism

---

## 1. Basic Components of Kafka

### Broker
Each server in a Kafka cluster is called a Broker.

### Topic
Logical classification of messages.

### Partition
A Topic is split into multiple Partitions.  
This is the foundation of Kafka's high throughput and high concurrency.

### Producer
Producer, responsible for sending messages.

### Consumer
Consumer, responsible for consuming messages.

### Consumer Group
Multiple consumers form a consumer group, and the group shares the consumption of multiple Partitions.

---

## 2. Why Kafka Has High Throughput
1. Topics are partitioned into Partitions, enabling parallel processing  
2. Sequential writes to disk, high I/O efficiency  
3. Batch sending and batch pulling, reducing network and disk overhead

---

## 3. Kafka Replication Mechanism

### Core Points
Kafka's replication is not "one master and one slave per machine," but rather:

> **Each Partition can be configured with multiple replicas.**

### Leader / Follower
For a specific Partition:
- One replica is the Leader  
- Other replicas are Follower

### External Read/Write
- Producers mainly write to the Leader  
- Consumers default read from the Leader  
- Follower replicas synchronize data from the Leader

### Fault Switching
If the Leader fails, a new Leader is selected from the synchronized Follower replicas.

---

## 4. What is ISR
ISR = **In-Sync Replicas**  
That is, "a collection of replicas that are in sync with the Leader."

Only replicas in sync are more suitable to become new Leader candidates.

### Interview Expression
Kafka does not immediately promote any Follower to Leader, but prefers to select new Leaders from ISR. This minimizes the risk of data loss.

---

## 5. Kafka's Reliability and ack

### acks=0
Producers send only, no confirmation expected  
High performance, lowest reliability

### acks=1
Leader confirms receipt  
If Follower hasn't synchronized, Leader failure may result in data loss

### acks=all
Requires higher-level confirmation  
Higher reliability

### Interview Expression
Kafka is not guaranteed to never lose data. Its reliability relates to replica factor, ISR status, and producer ack strategies. With proper configuration, data loss risk can be minimized.

---

## 6. Kafka Interview Quick Reference
- Kafka cluster consists of multiple Brokers  
- Topics are split into multiple Partitions  
- Partition is the basic unit for concurrency, scalability, and replication  
- Each Partition can be configured with multiple replicas  
- A Partition has only one Leader providing read/write at a time  
- Follower replicas synchronize data from the Leader  
- If Leader fails, a new Leader is selected from ISR  
- ack, replica factor, and ISR collectively affect reliability

---

# Five. Differences Between Redis and Kafka Replication Mechanisms

## Redis
- More like master-slave replication  
- Master handles writes, slaves replicate data  
- After failure, a slave promotes to master  
- Default asynchronous replication, may lose recent data

## Kafka
- More like multi-replica mechanism at Partition level  
- Leader provides read/write  
- Follower synchronizes data  
- If Leader fails, a new Leader is selected from ISR  
- Emphasizes message reliability and high throughput

### Interview One-Sentence Summary
Redis replication focuses more on data service high availability; Kafka replication focuses more on message partition redundancy and Leader switching.
