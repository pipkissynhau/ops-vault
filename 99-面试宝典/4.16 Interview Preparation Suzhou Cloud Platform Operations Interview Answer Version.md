# III. Linux Basic Operations Troubleshooting

## 1. How to troubleshoot high CPU usage on a production server

You can answer:

If a production server has high CPU usage, I generally follow several steps to troubleshoot.

First, I use top or htop to check overall CPU usage, confirming whether it's system-wide high or a specific process.

Second, I locate the specific process, check which PID is using high resources, and use ps, top -Hp, or pidstat to determine if it's a single-process issue or multi-threaded problem.

Third, I check what service this process is, then combine it with logs to determine if it's due to high business requests, program dead loops, slow SQL, or abnormal scheduled tasks.

For Java-based services, I further use jstack, GC logs, and thread status analysis. For system-level issues, I check iowait, context switching, and load metrics to determine if it's caused by IO or lock contention leading to false high CPU.

Finally, I handle it based on the findings, such as rate limiting, restarting abnormal processes, optimizing SQL, adjusting program logic, or coordinating with developers.

Interview one-sentence version:
First check overall status, then locate the process, combine with logs and business context to determine the cause, and handle it specifically.

---

## 2. How to troubleshoot a full disk

You can answer:

If the disk is full, I generally first use df -h to check which disk is full, then use du -sh combined with sort to find large directories.

I focus on several areas:
- Log directories
- Application upload directories
- Temporary file directories
- Docker / container data directories
- Database data directories

If logs are the cause, I first determine if logs are still being written, then decide whether to archive, truncate, or clean them, while checking if logrotate is configured. In container environments, I also check image, container logs, and overlay usage.

I prioritize ensuring the business disk isn't overwhelmed, then conduct root cause analysis, such as unconfigured log rotation, abnormal requests causing log explosion, or uncleaned backup files.

# IV. Application Deployment and Middleware Basics

## 1. How to deploy a Java project

You can answer:

For traditional Java projects, first confirm whether the delivery is a jar or war.

For jar packages, typically upload to Linux servers and start via java -jar or systemd management.

For war packages, place them in Tomcat's webapps directory, managed by Tomcat.

For external access, usually configure an Nginx in front for reverse proxy, load balancing, and static resource handling. During deployment, focus on:
- Correct configuration files
- Normal port listening
- Normal log output
- Normal Nginx forwarding
- Normal health checks and access verification

For containerized deployment, the process becomes image building, pushing to repository, pulling containers, or deploying to Kubernetes.

---

## 2. What is Nginx used for

You can answer:

Nginx has three common main functions.

First, it acts as a reverse proxy, forwarding external requests to backend application services like Tomcat, Spring Boot, or Go services.

Second, it provides load balancing, distributing requests to multiple backend instances to improve availability and throughput.

Third, it handles static resources like images, JS, and CSS, and is often used for HTTPS termination, URL forwarding, and access control.

Interview one-sentence version:
Nginx is essentially a reverse proxy and web service entry point.

---

## 3. What's the difference between Nginx and Haproxy

You can answer:

Nginx is more common in web scenarios, focusing on HTTP seven-layer proxy, and is commonly used for reverse proxy, static resource services, and HTTPS termination.

Haproxy is more focused on load balancing, supporting both four-layer and seven-layer, often used for pure traffic forwarding and high-performance load balancing in specialized proxy scenarios.

For conventional web application entry points, Nginx is very common; for scenarios more focused on high-performance TCP/HTTP load balancing and professional proxy, Haproxy is also common.

---

## 4. How do you understand Tomcat

You can answer:

Tomcat is essentially a Java Web container, commonly used for deploying Java Web applications in WAR package form. From an operations perspective, the main focus areas are:
- Deployment directory
- Port configuration
- JVM parameters
- Log path
- Thread pool
- Memory usage
- GC status

If the interviewer continues to ask about JVM, don't force a deep explanation. You can say:
"Regarding JVM, my main exposure has been from an operations perspective, such as memory parameters, GC logs, and application startup parameters. Deep tuning isn't my current most core focus area."

# FiveI don't know.Kubernetes and Docker

## 1. Differences between Docker and Kubernetes

You can answer like this:

Docker focuses more on container runtime and image delivery, solving the problem of "how to package applications and environments for execution."

Kubernetes focuses more on container orchestration platforms, solving the problem of "how to schedule multiple containers, how to scale, how to implement service discovery, and how to achieve high availability."

One-sentence understanding:
Docker is responsible for putting applications into containers, while Kubernetes is responsible for scaling container management.

---

## 2. Differences between Deployment and StatefulSet

Recommended answer:

Deployment is mainly used for stateless applications, such as Nginx, Web services, and API services. These applications typically don't rely on fixed identities or persistent storage, and Pod reconstruction with changed names has minimal impact.

StatefulSet is mainly used for stateful applications, such as MySQL, Redis, and Kafka. Its characteristics include:
- Fixed Pod names
- Relatively stable network identity
- Ability to bind fixed persistent storage

One-sentence summary:
Deployment manages stateless applications, while StatefulSet manages stateful applications.

---

## 3. What is the purpose of Service

You can answer like this:

Service mainly provides a stable access entry for a group of Pods. Since Pod IPs are dynamic, it's not advisable to directly depend on Pod IPs for external services. Service selects backend Pods through a selector and forwards traffic to them via ClusterIP, NodePort, or LoadBalancer.

One-sentence summary:
Service solves the problem of unstable Pods and the need for stable access entry.

---

## 4. What is the role of kube-proxy

Recommended answer:

kube-proxy's main role is to provide traffic forwarding capabilities for Kubernetes Services. When accessing a Service, requests are ultimately forwarded to backend Pods through the forwarding rules maintained by kube-proxy.

If the question continues:
You can add a sentence: Pod access to Service or node access to NodePort fundamentally relies on the forwarding capabilities maintained by kube-proxy.

---

## 5. What are the differences between the two modes of kube-proxy

Recommended answer:

kube-proxy commonly has two modes: iptables and IPVS.

The iptables mode uses a large number of iptables rules for traffic forwarding. Its advantage is simple implementation, but when Service, Endpoint, and Pod numbers grow, the rules will increase, leading to decreased matching efficiency.

The IPVS mode leverages Linux kernel's four-layer load balancing capabilities, maintaining Service and backend Pod mappings within the kernel. It offers better performance and scalability, making it more suitable for larger clusters.

One-sentence summary:
iptables is rule chain forwarding, while IPVS is kernel-level load balancing.

# SevenI don't know.Migration Methodology (This is your strength, make sure to explain clearly)

## 1. Have you done migrations

Recommended answer:

Yes, although I don't always directly use standard public cloud migration tools, actual projects are typically executed following migration methodologies.

Generally, we start by conducting a resource inventory of the source environment, such as systems, applications, data volume, and network dependencies, then prepare the target environment. During implementation, we typically first perform a full sync to migrate historical data; if the business is still running, we continue with incremental sync to keep up with changes in real-time.

During the cutover window, we pause business writes or stop source services, perform the final sync, then switch business entry points to the target environment. After the switch, we conduct data consistency and functionality verification, while also retaining rollback plans to prevent recovery issues if the switch fails.

This section is critical to practice thoroughly, as it's the most "project-experienced" response.

---

## 2. Differences between cold migration and hot migration

Recommended answer:

Cold migration involves stopping the business first, then migrating. The advantage is simple implementation and easier consistency guarantee; the disadvantage is noticeable business interruption.

Hot migration involves performing full and incremental sync during business operation, then completing the switch during the cutover window with a short downtime or stop-write. The advantage is shorter business interruption time, but the implementation complexity is higher.

One-sentence summary:
Cold migration focuses on planned downtime migration, while hot migration focuses on online synchronization followed by switch.

---

## 3. How to ensure migration consistency

Recommended answer:

Migration consistency is generally ensured through several measures.

First, perform a full sync to migrate historical data to the target environment.

Second, during business operation, use incremental sync to continuously synchronize changes.

Third, during formal cutover, pause writes and perform the final sync to avoid un-synced data from the source during the switch.

Finally, confirm consistency through data verification and functionality testing, such as record counts, key file hashes, and sampling comparisons of critical business data.

---

## 4. What are full sync, incremental sync, cutover, validation, and rollback

Recommended answer:

Full sync: Migrate existing historical data completely.
Incremental sync: Continue synchronizing new or changed data after the full sync.
Cutover: Officially switch business entry points from the source to the target.
Validation: Confirm data and functionality normalcy.
Rollback: If the target environment is abnormal, switch the business back to the source.

One-sentence summary:
First migrate existing data, then synchronize changes, switch during controlled windows, and ensure validation and rollback readiness.

---

## 5. How to perform OSS migration

Recommended answer:

OSS migration essentially belongs to object data migration. Generally, we first assess the source data scale, file count, directory structure, and file types, then prepare Bucket, permissions, and storage policies on the target side.

During implementation, we first perform a full sync to migrate historical objects; if the business is still writing, we continue with incremental sync to synchronize newly added or changed objects.

Switching will perform checks on object count, file size, and critical file hash values to confirm consistency before switching access points, such as domain names, CDN backsource, or application configurations.

One sentence:
The core of OSS migration is full, incremental, validation, and access switching.

# VIII. Database Key Weaknesses (This section is critical to focus on)

## 1) MySQL

### 1. What is MySQL Master-Slave Replication

Recommended answer:

MySQL master-slave replication is achieved through binlog. Write operations on the master are recorded in binlog, and the slave pulls binlog from the master via IO thread, then replays these logs via SQL thread to synchronize data.

It has two main purposes:
- Read-write separation
- High availability

If further asked about synchronization delay, you can answer:
There will be delays, especially when the master has high write pressure, the slave may experience replication lag.

---

### 2. What is binlog

Recommended answer:

binlog is MySQL's binary log, recording database change operations. It is mainly used in two scenarios:
- Master-slave replication
- Data recovery

In interviews, don't expand too deeply. Just explain "records changes, used for replication and recovery" is sufficient.

---

### 3. Why do read-write separation

Recommended answer:

Read-write separation mainly aims to reduce pressure on the master. Write requests still fall on the master, while read requests can be distributed to slaves, thus improving overall read capacity and system availability.

---

## 2) Redis

### 1. Difference between Redis Master-Slave and Cluster

Recommended answer:

Redis master-slave mainly addresses data replication and high availability. A master node can have multiple slave nodes, which replicate data from the master. It leans towards read-write separation and high availability but cannot truly solve single-machine capacity and write bottleneck issues.

Redis cluster achieves data sharding across multiple master nodes, with different keys distributed to different shards. It not only addresses high availability but also enables horizontal scaling.

One sentence:
Master-slave addresses high availability and read scalability, while cluster addresses sharding and scaling.

---

### 2. What is Redis Sentinel

Recommended answer:

Sentinel is used for Redis high availability. It monitors the status of master-slave nodes, and when the master node fails, Sentinel automatically elects a new master node and notifies clients to complete the switch.

One sentence:
Sentinel is the high availability management component for Redis master-slave architecture.

---

### 3. What are Redis persistence methods

Recommended answer:

Redis has two main persistence methods:

RDB: Periodically generates snapshots. Advantages are fast recovery, but data between snapshots may be lost in case of failure.

AOF: Records write operations in log format. Advantages are higher data safety, but files are larger and recovery is relatively slower.

---

### 4. What is a hot key in Redis

Recommended answer:

A hot key refers to a key with significantly higher access frequency than others, causing requests to concentrate on a single Redis node or shard.

It may lead to:
- Elevated node CPU
- Increased QPS
- Rising response latency
- Hot shard issues
- Cache penetration after key expiration

Solutions generally include:
- Local caching
- Multi-level caching
- Key splitting
- Asynchronous refresh
- Rate limiting

One sentence:
A hot key isn't about value size, but rather concentrated access.

---

## 3) MongoDB

### 1. What is MongoDB Replica Set

Recommended answer:

MongoDB replica set mainly addresses high availability. It typically consists of a master node and multiple slave nodes, with the master handling writes and slaves replicating data. If the master fails, a new master is automatically elected.

One sentence:
Replica set is essentially MongoDB's high availability solution.

---

### 2. What is MongoDB Sharding

Recommended answer:

MongoDB sharding mainly addresses data volume exceeding single-machine capacity, i.e., horizontal scaling.

Its core components include:
- Shard: Actual data storage node
- Mongos: Request router
- Config server: Stores shard metadata

Data is distributed across shards via shard key. In production environments, each shard is typically itself a replica set.

One sentence:
Replica set addresses high availability, while sharding addresses scaling.

---

## 4) Elasticsearch / ELK

### 1. Have you used ELK

Recommended answer:

Yes, mainly for log collection, storage, and query analysis. The typical pipeline is Filebeat or Logstash collecting logs, then writing to Elasticsearch, and Kibana for retrieval and display.

I've mainly encountered it from deployment, usage, and basic operations angles, with understanding of log collection pipelines and basic concepts.

---

### 2. What is an index in Elasticsearch

Recommended answer:

In Elasticsearch, an index can be likened to a table in relational databases, used to store a category of data. A document can be understood as a record, and fields as the individual fields in the record.

In log scenarios, indexes are typically created by day or business type, facilitating management, querying, and cleaning historical data.

---

### 3. What are shards and replicas in Elasticsearch

Recommended answer:

Sharding is mainly for expansion, splitting an index's data across multiple shards for storage, enabling horizontal scaling and improved processing capacity.

Replicas are mainly for high availability and read performance. A primary shard can have one or more replica shards. When a primary shard fails, replicas can take over.

One sentence:
Sharding addresses expansion, while replicas address high availability.

# IX. How to Answer Database Migration (This position may ask this)

Recommended answer:

Database migration typically doesn't involve a direct one-time switch, but rather a phased approach.

Usually, it starts with full migration, transferring historical data to the target database first. Then, through binlog or other incremental synchronization mechanisms, it continuously aligns data changes.

At final cutover, business writes are paused, and a final synchronization is performed to confirm the target database has caught up with the source. After switching business connections, data consistency verification is conducted, such as checking record counts, sampling critical business data, and functional validation. If anomalies are evident, there should be a rollback plan.

One sentence:
Database migration core is full, incremental, stop-write, switch, and validation.
