## 1. Pod Creation Process

### Interview Question
What is the process for creating a Pod?

### What This Question Really Tests
1. Whether you understand the entire lifecycle of a Pod from YAML to Running state.
2. Whether you distinguish between control plane and node responsibilities.
3. Whether you have a troubleshooting mindset, rather than just memorizing standard answers.

### Better Answer Approach
When answering this question, don’t start by reciting:
- apiserver
- etcd
- scheduler
- kubelet
- runtime
- CNI

Instead, provide your own framework first:

> I generally divide Pod creation into four steps: **object entry into the cluster, scheduling completion, node execution of creation, and status feedback**.

### Standard Interview Answer
I typically break down Pod creation into four stages: **object entry into the cluster, scheduling completion, node execution of creation, and status feedback**.

First, the user submits the Pod YAML to the apiserver, which performs authentication and validation. If everything is correct, it stores the Pod object in etcd. At this point, the Pod is not yet running; the cluster has only received the desired state.

Next, the scheduler checks for Pods that have not been assigned a node and selects an appropriate node based on resource availability, affinity rules, and tolerances. Once assigned, the kubelet on the target node creates the container, sets up networking and storage, and starts the container.

As the Pod starts, the kubelet continuously reports its status to the apiserver, eventually changing it from Pending to Running.

### Troubleshooting Perspective
From a troubleshooting perspective, issues at each stage of this process manifest differently:
- If scheduling fails, the Pod will remain in **Pending**.
- Image pulling failures result in **ImagePullBackOff**.
- Container startup failures often lead to **CrashLoopBackOff**.

Therefore, when troubleshooting, it’s essential to determine where the issue lies within this process.

### Review of This Question
The problem wasn’t that I didn’t know the answer; rather, my response was too generic.  
In the future, remember to:
1. First explain your framework.
2. Then describe the process.
3. Finally, add a troubleshooting perspective.

## 2. Will ipvs/iptables Rules on a Node Be Restored After a Restart?

### Interview Question
If the ipvs or iptables rules on a node are cleared, will they be restored after the node restarts?

### What This Question Really Tests
1. Whether you know who generates these rules.
2. Whether you understand that rules are dynamically synchronized by kube-proxy, not manually maintained.
3. Whether you have a problem-solving mindset.

### Key Conclusion
**Generally, they will be restored**, provided that kube-proxy is functioning properly and the node can successfully synchronize its cluster state with the apiserver.

### Standard Interview Answer
It depends on the circumstances. Typically, ipvs and iptables rules on nodes are not manually managed but are dynamically generated by **kube-proxy based on Service and Endpoint information**.

If the rules are cleared but kube-proxy continues to run normally, it will regenerate them during synchronization. If the node restarts and kube-proxy can retrieve the current Service and Endpoint states from the apiserver, the rules will also be re-generated. However, this is not always guaranteed. Issues such as a failed kube-proxy, communication problems between the node and apiserver, ipvs kernel module failures, or abnormal Service/Endpoint configurations could prevent rule restoration, causing service disruptions.

### Additional Troubleshooting Steps
When troubleshooting, I would check:
1. Whether kube-proxy is running normally.
2. Whether the node is ready for use.
3. Use commands like `iptables -t nat -L -n` or `ipvsadm -Ln` to verify rule status.
4. Ensure that Services and Endpoints/EndpointSlice are functioning correctly.
5. Verify the connectivity between the node and apiserver.

### Review of This Question
When answering this question, be specific about the prerequisites for restoration.  
Key terms to include:
- kube-proxy
- Service
- Endpoint
- dynamic synchronization
- conditional restoration
- troubleshooting approach

# III. Redis Cluster and Replication Mechanisms

---

## 1. Two Common High-Availability Modes of Redis

### 1) Master-Slave + Sentinel
Features:
- The master node is responsible for writing data.
- Slave nodes replicate the data from the master node.
- Sentinel is used for monitoring and failover.

Suitable for:
- High availability requirements.
- Read-write separation.
- Small to medium-scale deployments.

### 2) Redis Cluster
Features:
- It addresses both high availability and data sharding requirements.
- Not all data is stored on every node; instead, it is distributed across different master nodes.

---

## 2. Principles of Redis Cluster

Redis Cluster divides the key space into **16,384 hash slots**.  
When writing a key, a hash algorithm is used to determine which slot it belongs to, and then the data is written to the corresponding master node.

### Example
- master1 is responsible for managing some slots.
- master2 is responsible for managing some other slots.
- master3 is also responsible for managing some slots.

Each master node can have replicas attached to it for redundancy purposes.

### Interview Answer
The core of Redis Cluster lies in **sharding + replication**.  
It uses 16,384 hash slots to distribute data across multiple master nodes, and each master node has replicas to ensure high availability. This design allows for horizontal scaling and enables failover in case of a master node failure.

---

## 3. Redis Replication Technology

### Nature of Redis Replication
Redis replication is essentially **master-slave replication**.
- The master node is responsible for writing data.
- Slave nodes replicate the data from the master node.

### Synchronization Methods
#### 1) Full Sync
This usually occurs when:
- A slave node connects to a master node for the first time.
- There is a significant difference between the data on the master and slave nodes, making incremental synchronization impossible.

Process:
1. The slave node requests synchronization.
2. The master node generates an RDB file.
3. The master node sends the RDB file to the slave node.
4. The slave node loads the RDB file.
5. The master node then sends any write commands that occurred during the synchronization period.

#### 2) Incremental Sync
If the master and slave nodes have previously synchronized, and the master node still has historical data in its replication backlog buffer, only the differences between the data need to be synced.

---

## 4. Significance of Redis Replication
1. High availability.
2. Data redundancy.
3. Expansion of read traffic capacity.

---

## 5. Limitations of Redis Replication
Redis replication is **asynchronous by default**.  
This means that even if the data is successfully written to the master node, it does not necessarily mean that it has been completely replicated to all slave nodes.

Therefore, strictly speaking, Redis does not provide strong consistency. In case of a master node failure, **a small amount of recently written data may be lost**.

### Interview Answer
Redis master-slave replication is designed for eventual consistency rather than strong consistency. When the master node fails suddenly, there may be some recently written data that has not yet been replicated to the slave nodes.

---

## 6. Quick Interview Notes on Redis
- Redis master-slave replication ensures high availability.
- The master node writes data, and slave nodes replicate it.
- The first synchronization is usually full sync, followed by incremental sync if possible.
- Sentinel is primarily used for monitoring and failover in master-slave architectures.
- Redis Cluster uses 16,384 hash slots for data sharding.
- Each master node can have replicas attached to it.
- Redis replication is asynchronous by default, which may result in some data loss.

# IV. Kafka Cluster and Replication Mechanisms

---

## 1. Basic Components of Kafka

### Broker
Every server in a Kafka cluster is called a Broker.

### Topic
A logical classification of messages.

### Partition
A Topic is divided into multiple Partitions.  
This is the foundation for Kafka's high throughput and concurrency.

### Producer
A component that generates and sends messages.

### Consumer
A component that receives and processes messages.

### Consumer Group
Multiple consumers form a Consumer Group, which shares the responsibility of consuming multiple Partitions.

---

## 2. Reasons for Kafka's High Throughput

1. Topics are divided into Partitions, allowing parallel processing.
2. Messages are written to disk sequentially, improving IO efficiency.
3. Batch sending and batch pulling reduce network and disk overhead.

---
