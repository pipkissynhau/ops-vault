# 4.11-Interview Quick Notes on Monitoring Systems

## Document Description
This document is designed to address basic monitoring-related questions in interviews involving operations and maintenance, operational quality management, or platform operations and maintenance. The focus is not on in-depth architectural design but rather on helping to clearly explain the following aspects:
1. The concept of monitoring layering
2. The responsibilities of common components in the Prometheus ecosystem
3. The differences between Kubernetes and business monitoring
4. Monitoring perspectives in a shared-cluster environment for multiple businesses
5. Safe and appropriate ways to express these concepts during interviews

## I. When talking about monitoring, refer to it as a “layered system” rather than just a “tool”

In interviews, don’t start by only mentioning Prometheus and Grafana; instead, explain the concept of monitoring layering first.

### 1. Infrastructure Layer
Monitoring objects:
- Physical machines
- Virtual machines
- Linux hosts
- CPU
- Memory
- Disks
- Networks
- Inodes
- Load

Common components:
- node-exporter

Key points to emphasize:
- This layer primarily checks whether machine resources are in good health.
- It helps determine if there are resource bottlenecks on the host machine.
- Common issues include high CPU usage, insufficient memory, full disks, and network abnormalities.

### 2. Kubernetes Platform Layer
Monitoring objects:
- Nodes
- Pods
- Deployments
- StatefulSets
- DaemonSets
- PVCs/PVs
- HPA
- Container CPU/memory usage
- Pod restarts
- Scheduling status

Common components:
- kube-state-metrics
- cAdvisor
- kubelet metrics

Key points to emphasize:
- This layer focuses on the status of Kubernetes resource objects and the running status of containers.
- It helps identify whether the issue lies with the platform itself or with the business applications.

### 3. Middleware Layer
Monitoring objects:
- MySQL
- Redis
- Kafka
- Nginx
- Elasticsearch

Common components:
- mysqld-exporter
- redis-exporter
- kafka-exporter
- nginx exporter

Key points to emphasize:
- This layer monitors the status of individual middleware components.
- Examples include the number of connections, latency, slow queries, consumption backlogs, and master-slave status.

### 4. Business Application Layer
Monitoring objects:
- Interface success rate
- Response time
- Error rate
- Core service links
- SLA/SLO targets
- Whether users can actually use the service normally

Common methods:
- Exposing metrics directly from the application
- Using blackbox-exporters
- Analyzing logs
- Performing link tracing

Key points to emphasize:
- This layer truly reflects the availability of the business service.
- Just because a Pod is running doesn’t necessarily mean the service is functioning properly.
- Business monitoring cannot be solely based on Kubernetes resource monitoring.

## II. Responsibilities of common components in the Prometheus ecosystem

### 1. Prometheus
Function:
- Collects metrics.
- Stores time-series data.
- Handles PromQL queries.
- Provides data for alerts and visualizations.

One-sentence summary:
- Prometheus is responsible for data collection and storage.

### 2. Grafana
Function:
- Displays dashboards.
- Supports multi-dimensional filtering and visualization.
- Allows organizing dashboards by team, business, or topic.

One-sentence summary:
- Grafana is used for visualizing monitoring data.

### 3. Alertmanager
Function:
- Receives alerts generated by Prometheus.
- Groups, routes, suppresses, and sends notifications for these alerts.
- Integrates with tools like WeCom, Lark, Webhooks, and emails.

One-sentence summary:
- Alertmanager handles alert notification processes.

### 4. node-exporter
Function:
- Collects metrics at the node level.
- Examples include CPU, memory, disk, and network statistics.

One-sentence summary:
- node-exporter monitors machine resources.

### 5. kube-state-metrics
Function:
- Collects status information about Kubernetes resource objects.
- Examples include Pod, Deployment, Node, PVC, HPA status.

One-sentence summary:
- kube-state-metrics tracks the status of K8s objects.

### 6. cAdvisor
Function:
- Provides insights into container resource usage.
- Examples include CPU, memory, file system, and network traffic statistics.

One-sentence summary:
- cadvisor monitors container resources.

### 7. mysqld-exporter
Function:
- Connects to MySQL servers.
- Collects MySQL’s own metrics.
- Makes these metrics available for Prometheus to collect.

One-sentence summary:
- mysqld-exporter provides MySQL metrics for monitoring.

### 8. blackbox-exporter
Function:
- Conducts black-box#### 1. Overview Dashboard
See:
- Cluster Health
- Core Business Health
- Total Number of Alerts
- Trends in Core Resources

Function:
- Quickly identify where issues lie.

#### 2. Specialized Dashboards
For example:
- Node Resource Dashboard
- K8s Workload Dashboard
- MySQL Dashboard
- Redis Dashboard
- Ingress Dashboard

Function:
- Provide detailed insights into a specific area.

#### 3. Service-specific Dashboards
For example:
- A particular Business Application Dashboard
- A Specific Middleware Instance Dashboard

Function:
- Useful for specific business teams or component owners.

### Key Points
Not every object requires its own dashboard; many dashboards are templated and can be customized using variables such as:
- cluster
- namespace
- app
- workload
- pod
- instance

### Interview Answer
In production, there may be multiple dashboards, but they are typically structured into three levels: overview, specialized, and service-specific. Variables and alert links help reduce the need for manual page switching, saving time and effort.

## 9. How to Handle Multiple Businesses in One K8s Cluster
### This is a Common Scenario
A single cluster may host multiple systems simultaneously, such as:
- User Systems
- Order Management Systems
- Payment Systems
- Risk Control Systems
- Internal Systems
- Middleware Components

### How Monitoring Platforms Are Designed
Generally, a unified platform is used, but it can be divided based on dimensions such as:
- namespace
- app
- team
- environment
- service
- owner

### At the Basic Level
View global information such as:
- Nodes
- Cluster Resources
- Overall Pod Status
- kubelet / scheduler / etcd, etc.

### At the Platform Level
Support drilling down by namespace/workload/app.

### At the Business Level
Separate monitoring for each business:
- For Business A, focus on its interfaces, success rates, and error rates.
- For Business B, focus on its core processes.

### Standard Interview Answer
It's common to share one K8s cluster among multiple businesses. Monitoring platforms are usually unified but can be divided using namespace, labels, environment, and responsible teams. At the infrastructure/cluster level, view everything globally; at the business level, use dedicated dashboards and alerts for specific services.

## 10. Does Prometheus Have a Multi-account System?
### Conclusion
Prometheus itself does not provide a complete multi-tenant permission system.

### More Accurately
Prometheus is primarily designed for:
- Metric collection
- Time-series storage
- Querying

It is not specifically designed for strict business-level permission isolation, where users would only view data related to their own services.

### How It's Typically Used in Production
Grafana is often combined with Prometheus to control permissions at the user, team, folder, and dashboard levels. For example:
- Team A can only access dashboards related to Business A.
- Team B can only access dashboards related to Business B.
- The platform team has full access to all cluster monitoring.

### Standard Interview Answer
Prometheus is primarily used for data collection and storage and does not provide a complete multi-account system with business-level isolation. In production, Grafana is often used to implement permission controls at different levels, ensuring that each team can view only the data relevant to their responsibilities.

## 11. The Safest Way to Express One's Knowledge in Monitoring Interviews
This section is very important.

### Content That Can Be Mentioned as "Participated In/Was Involved With"
- Worked on Prometheus + Grafana projects
- Got familiar with node monitoring and K8s platform monitoring
- Understand the role of kube-state-metrics and node-exporter
- Contributed to basic alert rule configuration
- Handled release support, deployment troubleshooting, and monitoring analysis

### Content That Can Be Mentioned as "Understood/Has Basic Knowledge Of"
- The distinction between business monitoring and platform monitoring
- How to split monitoring perspectives in a multi-business cluster
- The basic workings of mysqld-exporter
- How Grafana organizes dashboards by business

### Content That Should Not Be Claimed as "Led"
- Complete design of monitoring platforms
- Development of monitoring permission systems
- Management of multi-tenant monitoring
- Governance of mature alert platforms
- Full ownership of business observability systems

### Core Principle
Only claim to have participated in or understood something; never claim to have led the development of anything outside your scope of responsibility.
