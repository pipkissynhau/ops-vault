# III. Linux Basic Operations Questions

## 1. How to troubleshoot high CPU usage on online servers?

You can answer like this:

If the CPU usage of an online server is high, I would start by following these steps:

First, use top or htop to check the overall CPU usage and determine whether it is due to the entire system or a specific process.

Next, identify the specific process with its PID and use ps, top -Hp, or pidstat to see if it is a single-process issue or a multi-threading problem.

Then, determine what service this process belongs to and check the logs to figure out whether it is caused by excessive business requests, infinite loops in the program, slow SQL queries, or abnormal scheduled tasks.

For Java services, I would further analyze jstack, gc logs, and thread status. For system-level issues, I would also look at indicators such as iowait, context switches, and load to determine if high CPU usage is due to IO or lock contention.

Finally, based on the findings, I would take appropriate actions such as implementing rate limiting, restarting abnormal processes, optimizing SQL queries, adjusting program logic, or coordinating with developers to resolve the issue.

In one sentence for the interview:
First, assess the overall situation; then identify the problematic process; analyze the logs and business context; and finally implement targeted solutions.

## 2. How to troubleshoot full disk space?

You can answer like this:

If the disk space is full, I would first use df -h to find out which partition is occupied, and then use du -sh with sort to identify large files or directories.

I would focus on checking the following areas:
- Log directories
- Application upload directories
- Temporary file directories
- Docker/container data directories
- Database data directories

If logs are taking up too much space, I would first check if they are still being written and then decide whether to archive, truncate, or clean them up. I would also verify if log rotation settings are in place. In a container environment, I would also consider the size of images, container logs, and overlay data.

MySQL:
- Master-slave architecture = binlog + IO thread + SQL thread.
- Functions = read-write separation + high availability.

Redis:
- Master-slave architecture = high availability / replication.
- Cluster configuration = sharding / scaling.
- Sentinel mechanism = automatic master selection.
- Hot keys = for frequent access.

MongoDB:
- Replica set = high availability.
- Sharding = scaling.
- Key components = shard, mongos, config server.

ES:
- Indexes = equivalent to tables in relational databases.
- Documents = individual records.
- Sharding = used for scalability.
- Replicas = ensure high availability.
- Logs are often indexed daily for efficient retrieval.

Data migrations:
- Steps include resource assessment, full data transfer, incremental updates, data cut-over, verification, and rollback if necessary.

OSS migration:
- Similar to data migrations but specifically for cloud object storage systems.
- Includes full migration, incremental synchronization, consistency checks, and switching of access paths.
