## 8. What are the common load balancing algorithms in Nginx?
Answer:
Common ones include:
1. Round Robin (default)
2. Weighted Round Robin
3. ip_hash, which assigns based on client IP
4. least_conn, which prioritizes servers with fewer current connections

### Round Robin Example
    upstream backend {
        server 10.0.0.11:8080;
        server 10.0.0.12:8080;
    }

### Weighted Round Robin Example
    upstream backend {
        server 10.0.0.11:8080 weight=3;
        server 10.0.0.12:8080 weight=1;
    }

### ip_hash Example
    upstream backend {
        ip_hash;
        server 10.0.0.11:8080;
        server 10.0.0.12:8080;
    }

### least_conn Example
    upstream backend {
        least_conn;
        server 10.0.0.11:8080;
        server 10.0.0.12:8080;
    }

## 14. What's the difference between bind mount and volume?
Answer:
Bind mount is explicitly mounting a host path into the container, suitable for configuration files, log directories, and data directories that need direct management.  
Volume is a Docker-managed data volume, suitable for container data persistence, such as database data directories.  
In actual use, I prefer to use bind mount for configuration files, and use bind mount or volume for data directories based on the scenario.

### Bind Mount Example
    docker run -d \
      -v /opt/nginx/nginx.conf:/etc/nginx/nginx.conf \
      -v /opt/nginx/html:/usr/share/nginx/html \
      nginx:latest

### Volume Example
    docker volume create mysql_data

    docker run -d \
      --name mysql \
      -e MYSQL_ROOT_PASSWORD=123456 \
      -v mysql_data:/var/lib/mysql \
      mysql:8

## 15. Why does mounting overwrite the container's original directory?
Answer:
Mounting essentially mounts a host directory or volume to a container path, which will overwrite the container's original directory rather than merging.  
If mounting an empty directory, it may cause the container to fail startup due to missing necessary files.  
In actual use, configuration files are usually mounted as single files, or the original configuration is copied out before mounting.

## 19. What is Prometheus?
Answer:
Prometheus is a monitoring system based on time-series data.  
It typically pulls metrics data from exporters exposed by monitored targets periodically, storing this data as time-series data.  
Then, based on pre-configured alerting rules, it determines if anomalies occur. If alerts are triggered, it forwards them to Alertmanager for grouping, deduplication, and notification delivery.  
Normally, it is combined with Grafana for monitoring dashboard visualization.

---

## 20. What is the overall flow of Prometheus?
Answer:
Monitored target  
→ exporter exposes metrics  
→ Prometheus periodically pulls metrics  
→ stores as time-series data  
→ determines if alerting based on rules  
→ Alertmanager sends alerts to DingTalk or email  
→ Grafana displays charts

## 24. Where are monitoring rules written? Where are alerting rules written?
Answer:
Prometheus' metric collection and monitoring configuration are generally written in prometheus.yml, with the focus on scrape_configs.
Alerting rules are usually written in separate rule files, such as rules/*.yml, and then referenced in prometheus.yml via rule_files.
Prometheus forwards alerts to Alertmanager after detecting matching rules.
Alertmanager's notification configuration is generally written in alertmanager.yml.

### prometheus.yml Example
    global:
      scrape_interval: 15s

    rule_files:
      - "rules/*.yml"

    alerting:
      alertmanagers:
        - static_configs:
            - targets: ['10.0.0.20:9093']

    scrape_configs:
      - job_name: 'node'
        static_configs:
          - targets: ['10.0.0.11:9100', '10.0.0.12:9100']

### Alerting Rule File Example rules/node_rules.yml
    groups:
    - name: node-alerts
      rules:
      - alert: HostHighCPU
        expr: 100 - (avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "High CPU Usage on Host"
          description: "{{ $labels.instance }} CPU has been over 80% for 5 minutes"

### alertmanager.yml Example
    route:
      receiver: 'default'

    receivers:
    - name: 'default'
      webhook_configs:
      - url: 'http://alertmanager-webhook-dingtalk:8060/dingtalk/webhook/send'

## 32. What does relabel_configs do?
Answer:
relabel_configs is a common configuration in Prometheus' automatic discovery scenarios, used to filter, rewrite, or label discovered targets.
For example, retaining only certain namespace Pods or converting metadata to labels.

### Kubernetes Pod Automatic Discovery Example
    scrape_configs:
      - job_name: 'kubernetes-pods'
        kubernetes_sd_configs:
          - role: pod

        relabel_configs:
          - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
            action: keep
            regex: true /think

- source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_path]
            action: replace
            target_label: __metrics_path__
            regex: (.+)

          - source_labels: [__address__, __meta_kubernetes_pod_annotation_prometheus_io_port]
            action: replace
            regex: ([^:]+)(?::\d+)?;(\d+)
            replacement: $1:$2
            target_label: __address__

### Example Pod annotations that need to be paired
    annotations:
      prometheus.io/scrape: "true"
      prometheus.io/port: "8080"
      prometheus.io/path: "/metrics"

## 49. What Is Output Redirection?
Answer:
Output redirection is writing command output to a file instead of printing it directly to the terminal.

### 1) Standard Output Redirection
    ls > file.txt

Explanation:
- Write normal output to file.txt
- Overwrite existing content

### 2) Append Output
    ls >> file.txt

Explanation:
- Append content, do not overwrite

### 3) Error Output Redirection
    ls /not_exist 2> error.log

Explanation:
- Write only error messages to error.log

### 4) Redirect Both Standard Output and Error Output
    ls /tmp /not_exist > all.log 2>&1

Explanation:
- > all.log: Write normal output
- 2>&1: Redirect error output to standard output
- All output is written to one file

### 5) Discard Output
    ls /tmp > /dev/null 2>&1

Explanation:
- Discard all output

---

## 50. What Does 2>&1 Mean?
Answer:
2>&1 means redirecting error output (2) to standard output (1).  
If standard output has already been redirected to a file, error output will also be written to that file.

### Example
    command > file.log 2>&1

Explanation:
1. Standard output is written to file.log
2. Error output is redirected to standard output
3. Both normal and error output are written to file.log

---

## 51. What Are Common Mistake Patterns?
Answer:
Common mistakes are:

    command 2>&1 > file.log

This order is incorrect because error output is first redirected to the current terminal's standard output, and later redirecting standard output to a file won't include error output in the file.

## 53. What Are the Differences Between Redis RDB and AOF?
Answer:
Redis persistence mainly includes RDB and AOF.

RDB is snapshot persistence, saving memory data to a dump.rdb file at a specific time.  
The save configuration item controls when a snapshot is triggered based on write operations.  
Its advantages are fast recovery and compact files, suitable for backups; the disadvantage is potential data loss after the last snapshot during a crash.

AOF is append-only log persistence, appending each write operation command to a log file.  
Its advantage is safer data, usually less data loss; the disadvantage is larger files and slower recovery speed compared to RDB.

In short, RDB focuses on snapshot backups and recovery efficiency, while AOF focuses on data safety.  
In production environments, both methods are often enabled together.

### You Can Also Add
Answer:
Redis has RDB as a common persistence method, and the save configuration item controls RDB snapshot triggers.  
But if the interviewer asks about the differences between RDB and AOF, the focus should be on mechanisms, pros/cons, and use cases, not just the save configuration.

## 58. How was data validation done?
Answer:
For data validation, we generally don't just check if data was transmitted, but confirm whether the transmitted data is complete, usable, and consistent.

In practice, we usually first synchronize data through the network, for example, using rsync for a full sync.
If there are changes on the source side before the formal switch, we do an incremental sync before the switch to minimize data differences during the final switch window.

After synchronization, we perform several layers of validation:

The first layer is checking if there were errors during the sync process;
The second layer is validating basic information consistency, such as file count, directory structure, and file size;
The third layer is doing hash value validation for key files or directories, such as md5 or sha256, to confirm content consistency between source and target.

For business system migration, we don't stop at the file level, and later combine it with business testing to confirm that the migrated data can be normally read and used by the application.

### Simplified answer
Answer:
We first synchronized data through the network, for example, using rsync for a full sync.
After synchronization, we validated consistency through file count, size, and hash values of key files.
If there were changes on the source side before the formal switch, we did an incremental sync before the switch, and finally confirmed data usability through business chain testing.
