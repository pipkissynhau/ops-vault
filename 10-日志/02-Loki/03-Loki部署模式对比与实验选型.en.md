The focus of this article is not to directly execute Helm installations but to first address the following issues:

- What are the different deployment modes of Loki?
- In what scenarios are Monolithic, Simple Scalable, and Microservices suitable respectively?
- Why is it not recommended to start with the Microservices mode in a learning environment?
- Why can't production environments be judged solely by whether something "works"?
- What is the relationship between Loki's deployment modes and storage methods?
- How do Loki's deployment modes affect log volume, query load, and operational complexity?
- How can we use Helm values and templates to observe the resources generated by different modes?
- Which mode should be chosen for this series of experiments?
- How can one evolve from a monolithic mode to object storage and higher availability modes in the future?
- How should learning and production decisions be made regarding Simple Scalable, now marked as being deprecated?

    Ingester

### 9.2 Independent Components

This architecture may include the following components:

- Distributor
- Ingester
- Querier
- Query Frontend
- Query Scheduler
- Compactor
- Ruler
- Index Gateway
- Gateway
- Memcached
- Canary

### 9.3 Advantages

Advantages of this microservices/distributed architecture include:

- Components can be independently scaled up or down.
- Query and write operations are more thoroughly isolated from each other.
- It is well-suited for large-scale logging platforms.
- It supports multi-tenancy scenarios.
- It handles high-concurrency queries efficiently.
- It allows platform teams to perform fine-grained optimization.
- It provides stronger fault isolation capabilities.

### 9.4 Disadvantages

Disadvantages of this architecture include:

- The deployment process is more complex.
- The configuration requirements are higher.
- There are many components and services involved.
- Troubleshooting can be more challenging.
- It relies more on object storage, caching, and networking resources.
- It requires a higher level of expertise from Ops personnel.---

## Chapter Ten: The Relationship Between Deployment Modes and Storage Methods

### 10.1 Local File System

Suitable for:

    Learning
    Temporary verification
    Minimum-scale experiments in monolithic mode

Advantages:

    Simple
    Requires little configuration
    Quick deployment

Disadvantages:

    Risk of Pod reconstruction
    Risk of node failures
    Limited capacity
    Not suitable for multiple replicas
    Not suitable for long-term storage in production environments

### 10.2 PVC

Suitable for:

    Enhancing learning environments
    Small-scale environments
    Persistent data in monolithic mode
    Initial verification and retention periods

Advantages:

    More reliable than `emptyDir`
    Data is retained after Pod reconstruction
    Native Kubernetes management

Disadvantages:

    Strongly dependent on the storage class
    Limited high availability
    Limited scalability
    Caution should be exercised when sharing multiple replicas
    Not as suitable for long-term log storage as object storage

### 10.3 Object Storage

Suitable for:

    Production use
    Medium to large-scale logs
    Multiple replicas
    High availability
    Long-term storage
    Capacity expansion

Common object storage solutions include:

    MinIO
    AWS S3
    Alibaba Cloud OSS
    Tencent Cloud COS
    Huawei Cloud OBS
    GCS
    Azure Blob

In this series, we use:

    MinIO

Reasons:

    Easy to deploy locally
    Compatible with S3
    Suitable for experiments
    Facilitates viewing data in buckets

### 10.4 Recommended Sequences

First step for learning:

    Monolithic + Local / PVC

Second step for learning:

    Monolithic + MinIO

For small to medium-scale production environments:

    Follow the official version roadmap and evaluate options like Monolithic HA + object storage or Microservices.

For large-scale production environments:

    Microservices / Distributed + object storage + caching + comprehensive monitoring

## Chapter Eleven: The Relationship Between Deployment Modes and Gateways

### 11.1 What is a Gateway?

A Gateway typically serves as a unified entry point in front of Loki.

A common implementation in Helm deployments is Nginx.

Its functions include:

    Receiving write requests
    Receiving query requests
    Forwarding them to the corresponding Loki backend based on the path
    Exposing a unified Service
    Simplifying client configuration

### 11.2 Why is a Gateway Needed?

Without a Gateway, the collection end would need to know:

    The addresses of the write and query components
    The address of the Ruler component
    The addresses of multiple Services

With a Gateway, the collection end only needs to know:

    `http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push`

Grafana only needs to configure:

    `http://loki-gateway.logging.svc.cluster.local`

### 11.3 The Role of a Gateway in Different Deployment Modes

**Monolithic mode:**

    The Gateway is optional.
    In small-scale scenarios, direct access to the Loki Service is possible.
    Using a Gateway allows early approximation of production environment settings.

**Simple Scalable mode:**

    The Gateway is very important.
    It is responsible for forwarding write and query requests to different components with appropriate roles.

**Microservices mode:**

    The Gateway is essentially an essential component of the unified entry point.
    It helps hide the complexity of the underlying backend components.

## Chapter Twelve: The Relationship Between Deployment Modes and Alloy

Alloy operates on the collection end and is not part of the Loki server deployment mode.

Regardless of the deployment mode used by Loki, Alloy is responsible for:

    Collecting logs from Pods
    Adding Kubernetes labels
    Forwarding logs to Loki

The only difference lies in the address used by Alloy for writing logs.

### 12.1 Monolithic mode

Alloy can write logs to:

    `http://loki.logging.svc.cluster.local:3100/loki/api/v1/push`

Or through a Gateway:

    `http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push`

### 12.2 Simple Scalable mode

Typically, logs are written through the Gateway:

    `http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push`

The Gateway then forwards the requests to the write component.

### 12.3 Microservices mode

Typically, logs are written through the Gateway:

    `http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push`

The Gateway then forwards the requests to the distributor component.

## Section Sixteen: Practical Observation Three: Observing Simple Scalable Resources Using Helm Templates

### 16.1 Creating a values File

Create:

    values-loki-scalable-observe.yaml

Example content:

    deploymentMode: SimpleScalable

    loki:
      auth_enabled: false

    read:
      replicas: 1

    write:
      replicas: 1

    backend:
      replicas: 1

    test:
      enabled: false

    monitoring:
      selfMonitoring:
        enabled: false
      lokiCanary:
        enabled: false

Note:

    The Simple Scalable configuration is currently marked as deprecated.
    This section is mainly used to observe the structure of read/write/backend resources.
    It is not intended as a primary deployment scheme for this series.

### 16.2 Rendering YAML

    helm template loki grafana/loki \
      -n logging \
      -f values-loki-scalable-observe.yaml \
      > loki-scalable-rendered.yaml

### 16.3 Checking read/write/backend Resources

    grep -n "loki-read" loki-scalable-rendered.yaml

    grep -n "loki-write" loki-scalable-rendered.yaml

    grep -n "loki-backend" loki-scalable-rendered.yaml

    grep -n "loki-gateway" loki-scalable-rendered.yaml

### 16.4 Checking Resource Types

    grep -n "^kind:" loki-scalable-rendered.yaml

    grep -n "kind: StatefulSet" loki-scalable-rendered.yaml

    grep -n "kind: Deployment" loki-scalable-rendered.yaml

    grep -n "kind: Service" loki-scalable-rendered.yaml

### 16.5 Expected Understanding

In the Simple Scalable mode:

    read is responsible for handling query paths.
    write is responsible for writing data.
    backend handles background tasks.
    gateway provides a unified entry point.
    The number of resources is significantly higher than in the Monolithic mode.
    When troubleshooting, it is necessary to determine whether the issue relates to read, write, or the backend.

## Chapter Twenty-Four: Production Considerations

### 24.1 Don't Judge the Production Level Only by Deployment Mode

A production-grade Loki depends not only on its deployment mode but also on the following factors:

    Storage reliability
    Data retention policies
    Query restrictions
    Write throttling
    Tag standards
    Self-monitoring
    Alert rules
    Access control
    Backup and recovery
    Runbooks
    The capability of the operations team

### 24.2 Object Storage is a Key Focus in Production

In production, pay special attention to the following aspects of object storage:

    Whether the bucket exists
    Whether the access key is correct
    Whether the secret key is secure
    Network accessibility
    Whether TLS settings are correct
    Object storage capacity
    Performance
    Delete permissions
    Lifecycle management policies

### 24.3 Tag Governance Is More Important Than the Number of Components

Improper tag design can severely impact Loki's functionality. High-risk tags include:

    request_id, trace_id, user_id, order_id, session_id, full_url, error_message, stacktrace

Recommended tags include:

    cluster, environment, namespace, pod, container, node, app, team

### 24.4 Query Restrictions Are Essential in Production

In production environments, it is necessary to limit the following aspects of queries:

    The maximum time range for a single query
    The maximum number of log lines per query
    Concurrent queries
    Query timeouts
    Query resources allocated per tenant
    Write rates per tenant
    Number of streams per tenant

Otherwise, large-scale queries can affect the overall performance of Loki.

### 24.5 Loki Must Be Monitored Closely

At a minimum, monitor the following metrics:

    Whether the Loki Pod is ready
    Gateway errors (5xx status codes)
    Write failures
    Query failures
    Query latency
    Memory usage of the Ingester
    Active streams
    Status of the Compactor and Ruler components
    Object storage errors
    PVC/disk utilization rates

## Chapter Twenty-Six: Summary

Loki offers several deployment options, each with its own use cases:

    **Monolithic Architecture:** Suitable for learning, small-scale environments, and quick validation.
    **Simple Scalable Architecture:** A historically used approach for medium to small-scale scaling but now marked as deprecated and requiring caution.
    **Microservices/Distributed Architecture:** Perfect for large-scale production environments with multiple tenants, high write volumes, and concurrent queries.

In this series, we adopted the following approach:

    **Early stages:** Monolithic architecture.
    **Data collection:** Grafana Alloy.
    **Querying:** Grafana Explore.
    **Storage evolution:** PVC/file systems → MinIO object storage.
    **Alerting:** Loki Ruler → AlertManager.

Our core principle was to build a functional foundation first, then gradually add advanced features such as tagging, querying, and monitoring. Avoid pursuing overly complex architectures from the beginning. True production capability lies in ensuring that logs are fully collected, tags are properly designed, queries are manageable, alerts are accurate, storage is reliable, costs are controlled, failures can be resolved efficiently, and operations are sustainable.

In the next chapter, we will delve into the practical aspects of deploying Loki in a Kubernetes environment, verifying its proper functioning at each step.
